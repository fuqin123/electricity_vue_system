## 一、项目简介

**一句话**：把车间的**电、水、汽**三类能源数据与**产量**数据在同一个平台上打通，用一块大屏做实时监控、
用一个后台做数据治理与台账管理，让能源管理员能指着数字说清「哪条线、哪个时段、浪费在哪」。

### 业务背景

饮料灌装产线的能耗成本集中在三块：**灌装与输送的电耗**、**杀菌与 CIP 的汽耗**、**冷却与清洗的水耗**。
原先这三类数据分散在不同班组的表里，且只有车间总表，拿到手时已经晚了 1—2 天，无法指导当班调整。
本系统把这些数据按**整点**收敛到同一口径下，解决三个具体问题：

1. **看得见**：单位电耗（kWh/千瓶）随时可查，低于/高于考核目标一眼可辨；
2. **说得清**：低产时段、停线窗口、电表缺失会被自动识别成告警，不需要人工翻表；
3. **算得准**：所有折算指标共用同一套口径，避免大屏、报表、台账三处数字对不上。

### 系统定位

| 维度 | 说明 |
| :--- | :--- |
| 部署方式 | 公司内网部署，不出企业网 |
| 使用场景 | 车间墙挂大屏（7×24 常亮） + 能源管理员桌面后台 |
| 架构模式 | 前后端分离（Django REST API + Vue3 SPA） |
| 数据频率 | 整点聚合；原始采样 60 秒（可配） |
| 本期范围 | **仅框架**：路由 / 菜单 / 页面骨架 / 跳转可通，业务函数留空，数据使用虚拟数据 |
| 访问控制 | 正式环境走公司统一身份认证（SSO），不允许独立账号体系 |

## 二、技术栈

### 2.1 总体

| 应用 | 技术选型 |
| :--- | :--- |
| 大屏 `frontend/apps/screen` | Vue 3.5 + Vite 6 + ECharts 5 + Pinia + Vue Router(hash) + VueUse + SCSS |
| 后台 `frontend/apps/admin` | Vue 3.5 + Vite 6 + Element Plus 2.9 + ECharts 5 + Pinia + Vue Router(history) + VueUse + SCSS |
| 共享层 `frontend/packages/shared` | TypeScript 类型、全局配置、Mock 数据引擎、API SDK、设计令牌 SCSS |
| 视频监控 | **go2rtc** 转流网关（RTSP → 浏览器可播协议）；大屏走 HLS → MJPEG 可校验链路 |
| 包管理 | pnpm workspace（monorepo，工作区根在 `frontend/`） |
| 类型校验 | TypeScript 5.7 + vue-tsc |
| 后端（v1.2.0 起采集，v1.2.1 起大屏真实数据 + 后台配置接口） | Django 5.1 + MySQL 8 + pymodbus（Modbus RTU over TCP）+ PyMySQL；接口文档走 OpenAPI/Swagger |

### 2.2 为什么大屏和后台分成两个应用

这是本项目最关键的一个架构决策，理由有三条：

1. **浏览模式不同**：大屏是 `hash` 路由、固定 1920×1080 舞台、等比缩放、无需服务端 rewrite 配置，
   直接拷到任意静态目录（Nginx / IIS / Tomcat / `file://`）即可运行；
   后台是 `history` 路由、响应式布局、需要服务端 history 回退。两者对部署环境的要求是冲突的。
2. **视觉体系不同**：大屏是深色科技风（深靛蓝画布 + 蓝紫/科技青和弦），
   后台是源力设计系统的亮色 B 端风格（主色源力蓝 `#1664FF`，仅亮色模式）。
   硬塞进一个应用会导致样式互相污染。
3. **优化目标不同**：大屏要长期挂机内存稳定、首屏快、离线可用；后台要按需加载、路由懒加载。

代价是构建产物有两份、公共组件不能直接复用。为此把**领域类型、全局配置、Mock 数据引擎、API SDK**
全部下沉到 `frontend/packages/shared`，两侧引用同一份源码，口径不会分叉。

### 2.3 大屏：为什么保留 1920×1080 固定舞台

大屏挂在车间不同尺寸的电视/拼接屏上。如果用响应式布局，同一块面板在不同分辨率下会得到不同的构图
（高度不够就压缩、宽度不够就换行），数字位置漂移，观感不专业。
因此沿用固定舞台 + 等比缩放：无论 1920×1080、2560×1440 还是 3840×2160，
**构图比例完全一致，只整体缩放**。

### 2.4 后台：视觉基准

严格对齐**源力设计系统（Yuanli Design System）**：

| 规范项 | 取值 |
| :--- | :--- |
| 主色 | 源力蓝 `#1664FF`（hover `#0055FF`） |
| 栅格 | 4px 基准（间距 4/8/12/16/20/24/32/40） |
| 顶栏高度 | 48px |
| 侧栏宽度 | 200px |
| 操作控件高度 | 32px |
| 圆角 | 4px（控件）/ 8px（弹窗） |
| 模式 | **仅亮色模式**，不提供暗色主题 |
| 状态色 | 成功 `#2A814B`、警告 `#BD7E00`、危险 `#D7312A` |

Element Plus 的主题变量在 `frontend/apps/admin/src/styles/element-override.scss` 中整体覆盖到上述色阶，
不需要逐个组件改样式。

### 3.1 为什么前端工作区根在 `frontend/` 而不是仓库根

后端是 Python（Django），与 Node 工具链完全无关。把 `package.json`、`pnpm-workspace.yaml`、
锁文件都收进 `frontend/`，`backend/` 保持纯净，两边互不污染：

- 在 `frontend/` 下 `pnpm install` / `pnpm build`，行为与单仓库一致；
- 在 `backend/` 下用 `pip` + `venv`，不会被 Node 依赖干扰；
- 部署时只需要前端产物，不必把后端也拉进 Docker 构建上下文（已由根 `.dockerignore` 排除）。

副作用是各 `vite.config.ts` 里的相对路径仍为 `../../packages/shared/src`
（因为 `frontend/apps/screen/` → `../../` = `frontend/`，层级没变），无需调整。

## 五、快速开始（本地开发）

### 5.1 安装依赖

```bash
# 注意：pnpm 工作区根在 frontend/ 下，不是仓库根
cd E:\能源产效管理平台\electricity_vue_system\frontend
pnpm install
```

首次安装约 3—6 分钟（视网络），后续增量秒级完成。

### 5.2 启动开发服务器

两个应用需要分别启动（端口不冲突，可以并行跑）：

```bash
# 终端 1 —— 大屏（默认 http://localhost:5173）
pnpm dev:screen

# 终端 2 —— 后台（默认 http://localhost:5174）
pnpm dev:admin
```

`vite.config.ts` 中 `server.host` 已设为 `0.0.0.0`，同网段的同事可直接用你的内网 IP 访问，
便于车间现场用电视调试大屏。

### 5.3 构建与本地预览

```bash
# 全量构建（大屏 + 后台）
pnpm build

# 单独构建
pnpm build:screen
pnpm build:admin

# 本地以生产模式预览构建产物
pnpm preview:screen     # http://localhost:4173
pnpm preview:admin      # http://localhost:4174
```

> ⚠ **`pnpm build` 是串行执行两个应用的，不要改成并行。**
> `vue-tsc` 单进程峰值内存可达 1.5GB，两个应用并行会触发换页，
> 构建时间从 25 秒涨到 10 分钟以上（实测踩坑，见 `docs/02` 的 B-201）。
> 同理 `pnpm typecheck` 也加了 `--workspace-concurrency=1`。

构建产物位置：

| 应用 | 产物目录 | 部署形态 |
| :--- | :--- | :--- |
| 大屏 | `frontend/apps/screen/dist/` | 任意静态目录，建议挂 `/screen/` |
| 后台 | `frontend/apps/admin/dist/` | 站点根或子路径，**必须配置 history 回退** |

### 5.4 类型校验与格式化

```bash
pnpm typecheck              # 全部工作区
pnpm -F @eep/screen typecheck
pnpm -F @eep/admin typecheck
pnpm format                 # prettier 格式化
```

### 5.5 大屏操作说明

## 六、配置说明

### 6.1 大屏核心配置：`frontend/packages/shared/src/config.ts`

所有可调参数集中在这一个文件，改配置不改逻辑。

| 配置项 | 说明 | 当前值 |
| :--- | :--- | :--- |
| `dataConfig.mode` | `'mock'` 用内置模拟数据；`'api'` 走真实接口 | `'mock'` |
| `dataConfig.refreshMs` | 大屏自动刷新间隔（下限保护 6000ms） | `60000` |
| `energyModel.baseLoadKwhPerHour` | 单线基础负荷（待机/辅机/液压） | 20 kWh/h |
| `energyModel.variableKwhPerBottle` | 单线变动电耗（灌装+输送+在线包装） | 0.0068 kWh/瓶 |
| `energyModel.waterPerBottleL` | 车间水耗强度（含 CIP、冷却） | 2.8 L/瓶 |
| `energyModel.steamPerBottleKg` | 车间汽耗强度（含杀菌、CIP） | 0.21 kg/瓶 |
| `energyModel.targetUnitKwh` | 单位电耗考核目标 | 8.20 kWh/千瓶 |
| `thresholds.unitKwhHigh` | 单位电耗告警上限 | 9.60 kWh/千瓶 |
| `thresholds.outputLowRate` | 低产判定（占额定比） | 75% |
| `linesConfig[].rated` | 各线额定产能 | 18000—30000 瓶/时 |

> ⚠ **上线前必须用真实历史数据回填 `energyModel` 中的强度参数与 `thresholds` 中的阈值。**
> 当前的 0.0068 kWh/瓶、2.8 L/瓶等是行业经验值，直接用于考核会失真。

### 6.2 环境变量

前端项目本身**不依赖任何环境变量**（无密钥、无数据库连接）。
接口地址通过以下两种方式之一指定，二选一即可：

**方式 A：修改 `dataConfig.mode` 与 `api` 路径**（推荐，跟随构建产物走）

```ts
// frontend/packages/shared/src/config.ts
export const dataConfig = {
  mode: 'api',
  api: {
    overview: '/api/energy/overview',
    line: '/api/energy/line/{lineId}',
    hourly: '/api/energy/hourly'
  },
  refreshMs: 60000
};
```

**方式 B：开发期用 Vite 代理**（免后端 CORS 配置）

```ts
// frontend/apps/screen/vite.config.ts 或 frontend/apps/admin/vite.config.ts
server: {
  proxy: {
    '/api': { target: 'http://127.0.0.1:8000', changeOrigin: true }
  }
}
```

> 后端必需配置：**CORS 白名单、SQL 注入防护、所有接口鉴权（白名单接口需评审通过）**。

### 6.3 视频监控配置（go2rtc）

这里有一个必须先理解的事实：

> **浏览器不能直接播放 `rtsp://`。**
> 这不是前端能力问题，是浏览器的协议支持问题：`<video>` 只认 HLS / DASH / MP4；
> FLV 需 `flv.js` 解封装；MSE 需 fMP4 分片喂给 `SourceBuffer`；WebRTC 需网关提供信令。
> 所以 RTSP **必须经流媒体网关转协议** —— 这跟前端无关，是部署环节的事。

本项目采用 **go2rtc**，现场已在 `E:\能源产效管理平台\go2rtc_win64` 验证通过。

```
摄像头 (RTSP)  →  go2rtc 网关 (:1984)  →  浏览器（大屏 / 后台）
                                          大屏：按 mse → hls → mjpeg 自动降级
                                          后台预览：mse（iframe 内置播放页）
```

**四种输出协议对比（决定优先级顺序的依据）：**

| 协议 | 延迟 | 需要的端口 | 前端实现 | 能否校验出画 | 评价 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **hls** | 3—8 s | 仅 1984 | hls.js 直接拉流 | ✅ `videoWidth > 0` | **大屏默认首选**：兼容性最好，且能自己判断有没有画面 |
| **mjpeg** | 1—2 s | 仅 1984 | `<img>` 直接拉流 | ✅ 收到真实帧才触发 `load` | **大屏兜底**：任何浏览器都能显示；码率高、无音频 |
| mse | 0.5—2 s | 仅 1984 | iframe 载入内置播放页 | ❌ 跨域不可观测 | 延迟最低，但「只有声音没有画面」无法被前端发现。后台预览用它 |
| webrtc | < 0.5 s | 1984 + 8555 | iframe 载入 `/webrtc.html` | ❌ 跨域不可观测 | 延迟最低，但受 NAT 影响，要先放开 8555 |

> **为什么大屏不默认用 mse（v1.1.1 的调整，见 `02` 的 B-207 / ADR-008）**：
> mse / webrtc 由 go2rtc 内置播放页承载在**跨域 iframe** 里，父页面拿不到任何画面信息，
> `iframe.onload` 只能证明「网页加载成功」。一旦出现「有声无画」，
> 降级链会把它当成播放成功并卡死在第一档 —— v1.1.1 排查时正是它挡住了真正的原因
> （那次的实际根因是**视频容器高度被算成 0**，见 B-209，与协议无关）。
>
> 所以现在大屏默认只用**能自证有画面**的协议（hls / mjpeg），
> 并把 mse / webrtc 变成现场排查项：大屏上按 **V** 键循环切换链路
> （hls / mse / webrtc / 仅 mjpeg），选择存 localStorage。
> 若确认现场大屏用 mse 也能出画面，把 `videoConfig.prefer` 改成 `['mse', 'mjpeg']`
> 即可拿回 0.5—2s 的低延迟。

**为什么 mse / webrtc 走 iframe 而不由前端自己实现：**
MSE 需要把 WebSocket 收到的 fMP4 分片喂给 `SourceBuffer`，而
`MediaSource.isTypeSupported('video/mp4; codecs="avc1.64001f,mp4a.40.2"')`
里的 codec 串随摄像头编码档位（baseline / main / high）而变，写死会在某些型号上直接黑屏。
交给 go2rtc 自带脚本判断最稳。

> 两个反直觉点：
> ① `stream.html?src=X&mode=mse` 里的 `mode` 是**白名单**语义
> （go2rtc 的 `video-stream.js` 只认 `mode` 里列出的协议），
> 只写 `mse` 就是「MSE 不可用则彻底不播」，**不会自动往后降级**。
> ② **MJPEG 与抓图依赖网关侧的 ffmpeg。** 现场网关（go2rtc 1.9.14）**未安装 ffmpeg**，
> 实测 `/api/stream.mjpeg` 返回空响应、`/api/frame.jpeg` 返回 500
> （`exec: "ffmpeg" executable file not found`）。HLS 与 MSE 不依赖 ffmpeg，
> 画面不受影响，但后台「抓图」按钮会失败。

**前端配置（`frontend/packages/shared/src/config.ts`）：**

```ts
export const videoConfig = {
  enabled: true,
  provider: 'go2rtc',                          // 'go2rtc' | 'custom' | 'off'
  prefer: ['hls', 'mjpeg'],                    // 降级顺序（两者都可校验出画）
  go2rtc: {
    base: 'http://10.113.1.61:1984',           // ← 网关地址
    apiPort: 1984,
    webrtcPort: 8555
  },
  channels: {
    A1: { channel: 'CH01', stream: 'my_camera',        // ← 必须与 go2rtc.yaml 的 key 一致
          rtsp: 'rtsp://admin:***@10.113.1.118:554/Streaming/Channels/102',
          resolution: '1920×1080', fps: 25, codec: 'H.264' },
    A2: { channel: 'CH02', stream: 'my_camera', rtsp: '', resolution: '1920×1080',
          fps: 25, codec: 'H.264', enabled: false }    // ← 摄像头未到位时置 false
  },
  customEndpoints: { /* provider = 'custom' 时使用，兼容 MediaMTX / ZLMediaKit */ }
};
```

**网关配置（`deploy/go2rtc/go2rtc.example.yaml`）：**

```yaml
api:
  listen: ":1984"
  origin: "*"                                    # 前端直连网关需要跨域
webrtc:
  listen: ":8555"
streams:
  my_camera:
    - rtsp://admin:密码@10.113.1.118:554/Streaming/Channels/102   # 102 = 子码流
```

> **注意**：海康/大华摄像头默认并发路数有限（常见 4—6 路），每路流被一个播放端占用一份并发。
> go2rtc 默认按需拉流（无人观看自动断开），本项目大屏也只在打开单线详情时才播放。
> 墙挂大屏建议用**子码流**（`Channels/102` 而非 `101`），带宽与并发压力都小得多。

**完整排障手册见 `deploy/go2rtc/README.md`。** 新增一路摄像头的步骤：

1. 网关侧：`go2rtc.yaml` 的 `streams` 下加一行（如 `a2: rtsp://...`），重启网关；
2. 前端侧：`config.ts` 把 `channels.A2.stream` 改为 `a2`、`enabled` 改为 `true`；
3. 验证：后台「视频监控」页点「检测网关」，A2 行的「配置校验」应变为「正常」。

## 七、数据口径约定（对接后端必读）

这是本项目最容易出错的地方，后端与采集侧务必按同一口径实现。

### 7.1 采集侧建议

| 指标 | 数据源 | 采集频率 |
| :--- | :--- | :--- |
| 产线电量 kWh | 产线配电柜智能电表（Modbus TCP / 电力仪表网关） | 整点累加，或 15min 累加后整点聚合 |
| 产线产量 瓶 | 灌装机计数器 / 装箱机 PLC / MES 班次报工 | 整点 |
| 车间用水 t | 车间进水总表（电磁流量计） | 整点 |
| 车间用汽 t | 蒸汽总表（涡街 / 孔板流量计，**必须带温压补偿**） | 整点 |

### 7.2 三条硬性口径

1. **电表是累计值，入库前必须差分。**
   智能电表上报的是总有功电能（只增不减）。换表、归零、通讯中断都会在差分后产生**尖峰**，
   采集侧必须加异常值过滤（例如单小时电量超过额定产能对应能耗的 2 倍即判为异常并置空）。

2. **水、汽只有车间总表，不可拆分到线别。**
   所以大屏上「水耗/汽耗」永远只出现在车间级面板，单线详情页不显示这两项。
   折算方式是「车间合计产量 × 强度系数」，不是实测线别数据。

3. **未采集到的时段必须置 `null`，不要补 0。**
   前端按 `future: true` 渲染成虚线柱（计划态）与灰色行。
   如果后端补 0，大屏会显示成「产量暴跌到 0」，属于造假曲线。
   接口契约详见 `frontend/packages/shared/src/types.ts` 中的 `EnergySnapshot`。

### 7.3 接口返回结构

`GET /api/energy/overview` 直接返回与 `buildSnapshot()` **同构**的对象：

## 八、常见问题

### Q1. `pnpm install` 报 `ERR_PNPM_IGNORED_BUILDS`

pnpm v10+ 默认禁止依赖执行 `postinstall`。本项目已在 `pnpm-workspace.yaml` 中用 `allowBuilds` 放行
`esbuild` / `vue-demi` / `@parcel/watcher`，正常情况下不会再报。
若仍出现，检查该文件是否被 Git 合并冲突改坏。

### Q2. 依赖装完了但 `Cannot find module 'vue'` / `xxx is not recognized`

Windows 未开启「开发者模式」时，pnpm 默认的**符号链接式** `node_modules` 会因为权限不足
而只创建出**空目录**。本项目已在 `pnpm-workspace.yaml` 中设置 `nodeLinker: hoisted` 规避。
若仍出现，彻底清理后重装：

```bash
rm -rf node_modules apps/*/node_modules packages/*/node_modules pnpm-lock.yaml
pnpm install
```

### Q3. 修改了 `pnpm-workspace.yaml` / `.npmrc` 但没生效

pnpm v10 起，**工作区级设置以 `pnpm-workspace.yaml` 为准**，`.npmrc` 中的同名项会被忽略
（`registry` 除外）。新增设置请写进 `pnpm-workspace.yaml`。

### Q4. 后台刷新子路由 404

`history` 模式需要服务端把未命中的路径回退到 `index.html`。
Nginx 见 `04-版本部署-Linux版.md`，IIS 见 `03-版本部署-Windows版.md`。

### Q5. 大屏图表不显示，提示「图表库 ECharts 未加载」

这是旧版原生实现（CDN 加载）的降级提示。Vue 版本已把 ECharts 作为 npm 依赖打进产物，
不会出现该情况；若出现说明构建异常，重新 `pnpm build:screen`。

### Q6. 大屏在小分辨率屏上四周有黑边

属**预期行为**。舞台固定 1920×1080 等比缩放，宽高比不匹配时必然留边。
若屏是 16:9（1920×1080 / 2560×1440 / 3840×2160）则完全无黑边。
非 16:9 的屏请在浏览器里按 `F` 全屏后由浏览器做裁切。

### Q7. `pnpm build` 卡住十几分钟不结束

两个应用的构建**并行执行**时，`vue-tsc` 各占 1.5GB 左右内存，8GB 机器会触发换页。
本项目已把 `pnpm build` 改为串行（`pnpm build:screen && pnpm build:admin`）。
若你手工执行了并行命令导致卡住，等一会儿或直接杀掉重跑即可，不会损坏产物。

### Q8. 大屏视频区域显示「所有协议均无法播放」

按占位里给出的「失败记录」排查，常见顺序：

1. 网关是否在跑 —— 浏览器打开 `http://<网关IP>:1984/` 能否看到 go2rtc 首页；
2. 流名是否一致 —— `http://<网关IP>:1984/api/streams` 返回的 key 必须与
   `config.ts` 的 `channels.<产线>.stream` 完全相同（大小写敏感）；
3. 网关能否拉到摄像头 —— 看 go2rtc 控制台日志里的 `[rtsp]` 报错。

完整排障见 `deploy/go2rtc/README.md`。

### Q9. 大屏视频「只有声音、没有画面」（或后台能看、大屏看不到）

v1.1.1 已经修过这一类问题，**根因是视频容器高度被算成 0**（详见 `02` 的 B-209），
不是摄像头或网关故障。判断与处置：

1. 先看面板右上角角标：`HLS` / `MJPEG` 表示前端已确证收到画面帧；
   角标显示的协议若为 `MSE` / `WEBRTC`，请注意它由跨域 iframe 承载，**前端无法校验画面是否真的出来了**
   （鼠标悬停角标有提示）；
2. 若黑屏有声、角标又不是 `MJPEG`，按 **V** 键切换链路逐个试：
   默认链路是 `MSE → HLS → MJPEG`，V 键可切到 `HLS → MJPEG`（只用好校验的协议）；
3. 若默认链路也黑屏，看占位里的「失败记录」，它会直接写出原因：
   - 「只收到音频轨道」→ 浏览器不支持摄像头当前的视频编码，会自动继续降级到 MJPEG；
   - 「MJPEG 拉流失败（网关需安装 ffmpeg…）」→ 网关缺 ffmpeg（现场实测确实缺）；
   - 「HLS 致命错误 manifestLoadError」→ 浏览器**根本没连上网关**，
     常见于页面是 `localhost`/公网而网关在内网私有网段（浏览器会拦跨网段请求），
     或公司代理不允许访问内网地址；
   - 「video 解码失败（MediaError code=…）」→ 取值 3 解码失败、4 格式不支持；
4. 想用回低延迟：确认现场大屏切到 `MSE → MJPEG` 链路后确实出画面，
   再把 `videoConfig.prefer` 改成 `['mse', 'mjpeg']`（改配置即可，不用改代码）。

> 另外**排查时别忘了先量一下视频容器的实际尺寸**：
> 容器塌成 0 高时，症状与「编码不支持」「网络不通」完全一样（都有声音、都没画面）。
> 浏览器 F12 选中`.video` 看 `getBoundingClientRect()` 是最快的一步。
