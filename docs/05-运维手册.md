## 三、日常巡检

### 3.1 每日巡检（建议 08:30 前完成）

| # | 检查项 | 方法 | 合格标准 |
| :--- | :--- | :--- | :--- |
| 1 | 大屏是否在播 | 现场目视 or 远程截图 | 画面正常，无黑屏/无「数据获取失败」 |
| 2 | 大屏数值是否在动 | 观察 1—2 分钟 | 时钟在走、数字随整点更新 |
| 3 | 后台是否可登录 | 打开 `/admin/` | 正常进入登录页 |
| 4 | 服务是否存活 | `systemctl is-active nginx eep-backend` | 全部 `active` |
| 5 | 网关在线数 | 后台 → 设备与采集 → 采集网关 | 在线数 = 总数 |
| 6 | 未处理告警 | 后台 → 告警管理 → 实时告警 | 全部已确认或已恢复 |
| 7 | 数据完整率 | 后台 → 设备与采集 → 数据质量 | 平均完整率 ≥ 98% |
| 8 | 磁盘空间 | `df -h` | 使用率 < 80% |
| 9 | 备份是否生成 | `ls -lht /opt/eep/_backup \| head` | 有当天的备份记录 |
| 10 | 周期汇总是否结算过 | `tail -3 backend/logs/rollup-task.log`（任务 `EEP-Rollup`，每天 00:30） | 最后一行是**今天**的「结束：正常」。停了这个任务，大屏与后台的「近 30 日 / 近 12 月」会停在最后一次结算的那一天，**且不报任何错** |

**一键巡检脚本**（建议配成 cron / 定时任务）：

```bash
#!/usr/bin/env bash
# /opt/eep/ops/daily-check.sh —— 每日巡检
set -uo pipefail

echo "════════ 能源产效管理系统 · 每日巡检 $(date '+%F %T') ════════"

echo "── 1. 服务状态 ──"
for svc in nginx eep-backend; do
  state=$(systemctl is-active "$svc" 2>/dev/null || echo "not-found")
  [[ "$state" == "active" ]] && echo "  ✓ $svc : active" || echo "  ✗ $svc : $state"
done

echo "── 2. HTTP 探测 ──"
probe() {
  local url="$1" name="$2"
  local code
  code=$(curl -s -o /dev/null -m 10 -w "%{http_code}" "$url" || echo "000")
  [[ "$code" == "200" ]] && echo "  ✓ $name : $code" || echo "  ✗ $name : $code  ($url)"
}
probe "http://127.0.0.1/healthz"            "健康检查"
probe "http://127.0.0.1/screen/"            "大屏首页"
probe "http://127.0.0.1/admin/"             "后台首页"
probe "http://127.0.0.1/admin/system/user"  "后台子路由回退"
probe "http://127.0.0.1/api/health"         "后端 API"

echo "── 3. 磁盘空间 ──"
df -h / /opt 2>/dev/null | awk 'NR==1 || /\//'

echo "── 4. 备份情况 ──"
if [[ -d /opt/eep/_backup ]]; then
  cnt=$(ls -1 /opt/eep/_backup/*.tar.gz 2>/dev/null | wc -l)
  latest=$(ls -1t /opt/eep/_backup/*.tar.gz 2>/dev/null | head -1)
  echo "  备份份数：$cnt"
  [[ -n "$latest" ]] && echo "  最近备份：$(basename "$latest")  $(stat -c %y "$latest" | cut -d. -f1)"
else
  echo "  ✗ 备份目录不存在"
fi

echo "── 5. 后端错误日志（近 1 小时）──"
if command -v journalctl >/dev/null 2>&1; then
  n=$(journalctl -u eep-backend --since "1 hour ago" -p err --no-pager 2>/dev/null | wc -l)
  echo "  错误条数：$n"
  [[ "$n" -gt 0 ]] && journalctl -u eep-backend --since "1 hour ago" -p err --no-pager | tail -20
fi

echo "════════ 巡检结束 ════════"
```

### 3.2 每周巡检

- [ ] 检查 Nginx 错误日志中的异常趋势（`grep -c " 5[0-9][0-9] " /var/log/nginx/eep-access.log`）
- [ ] 检查后端慢接口（access log 中 `rt=` 大于 3 秒的请求）
- [ ] 核对后台「数据质量」页的缺失时段，逐条确认原因并闭环
- [ ] 检查磁盘 inode 使用率（`df -i`）—— 日志过多时会先耗尽 inode
- [ ] 抽查 2—3 天的历史数据与现场抄表记录是否一致
- [ ] 确认备份文件可解压（抽验一个）

### 3.3 每月巡检

- [ ] 第三方依赖 CVE 巡检（`pnpm audit` 或对应工具的漏洞库）
- [ ] 日志归档与清理，确认 `logrotate` 生效
- [ ] 阈值参数复核（与能源管理员共同确认是否需调整）
- [ ] 备份恢复演练（在测试环境实际恢复一次）
- [ ] 证书有效期检查（如启用 HTTPS）
- [ ] 账号权限复核（离职/调动人员及时回收）
- [ ] 大屏终端硬件检查（散热、屏幕烧屏、网线）

## 四、监控与告警

### 4.0 系统现在到底会自己报什么（v1.5.4 起）

告警引擎已落地，**站内告警**（后台「告警管理 → 实时告警」+ 大屏告警条）会自动生成下面 6 类，
全部来自实测数据而不是人工登记：

| 告警 | 什么情况会报 | 第一步该查什么 |
| :--- | :--- | :--- |
| 计量点未接入 | 表在台账里启用了，但**从未成功采到一次读数** | 接线 / 从站号 / 该表所在网关是否通；注意它**不参与合计**，所以界面上不会体现这块表 |
| 计量点采集失败 | 最近一轮采集失败，带出错误原因与最近成功时刻 | 报文与从站号；错误原因直接抄在告警内容里 |
| 网关整轮采集失败 | 该网关最近一轮点位**全部失败（0/N）** | 串口服务器 IP/端口、是否掉电。⚠ 与网关列表页的「在线」徽标不是一回事 |
| 采集停摆 | 最新成功读数超过 `collect.stale_alert_hours` 没更新 | 采集计划任务 / collector 容器是否还活着 |
| 小时数据不可信 | 近 24 小时出现**累计值回退（换表/清零）或异常尖峰** | 是否换过表、寄存器配置与倍率是否填错 |
| 周期覆盖率不足 | 昨日日汇总 `covered < expected`，即日合计少算了若干小时。**只在 00:30 日终结算后判定**（v1.5.5 起，结算前的当天快照不会误报） | 昨天哪些小时缺数、采集是否停过 |

巡检命令（只查不采，不会去碰设备）：

```bash
python manage.py check_alerts            # 或容器化部署：
docker compose exec backend python manage.py check_alerts
```

⚠ **通知渠道（邮件 / 企业微信 / 电话）尚未实现**，目前只有站内告警与接口读取。
下面 §4.2 描述的是设计目标，别当成已生效的能力。

### 4.1 建议监控指标

| 层级 | 指标 | 阈值 | 处置 |
| :--- | :--- | :--- | :--- |
| 服务 | Nginx 存活 | 任意时刻不可用 | 立即重启 + 查 error.log |
| 服务 | 后端存活 | 任意时刻不可用 | 重启 + 查 journalctl |
| 服务 | `/healthz` 响应时间 | > 3 s | 排查磁盘 / 负载 |
| 接口 | `/api/*` 5xx 比例 | > 1% | 查后端日志 |
| 接口 | 平均响应时间 | > 2 s | 查慢查询 / DB 连接池 |
| 主机 | CPU 使用率 | > 80% 持续 10 分钟 | 定位进程 |
| 主机 | 内存使用率 | > 85% | 查内存泄漏 / 提高配置 |
| 主机 | 磁盘使用率 | > 80% | 清理日志与备份 |
| 主机 | inode 使用率 | > 85% | 清理小文件（日志碎片） |
| 业务 | 采集网关在线率 | < 100% | 联系电气排查 |
| 业务 | 数据完整率 | < 98% | 见 §6.4 |
| 业务 | 未处理严重告警 | > 0 持续 1 小时 | 升级通知 |
| 业务 | 大屏心跳 | 连续 2 分钟无请求 | 现场确认终端是否断网/黑屏 |

### 4.2 告警通知渠道（⬜ 尚未实现，以下为设计目标）

按《代码仓库管理规范》对定时任务的强制要求：**失败必须有告警（邮件 / IM / 电话）**。
通知渠道在后台「系统管理 → 系统参数」的 `alarm.notify.channels` 中配置，当前值 `mail,wecom`。

| 级别 | 通知方式 | 响应时限 |
| :--- | :--- | :--- |
| 严重（critical） | 邮件 + 企业微信 + 电话 | 15 分钟内首响 |
| 重要（major） | 邮件 + 企业微信 | 30 分钟内首响 |
| 次要（minor） | 企业微信 | 4 小时内处理 |
| 提示（info） | 仅站内 | 次日处理 |

## 五、告警处置流程

### 5.1 通用处置流程

```
告警产生
   │
   ├─ ① 初判：是「真实业务异常」还是「采集链路异常」？
   │     看后台 → 设备与采集 → 数据质量
   │     · 完整率 100%  → 真实业务异常，转 ②
   │     · 有缺失时段    → 采集链路异常，转 ③
   │
   ├─ ② 业务异常处置（能源管理员）
   │     · 单位电耗超阈值 → 核对当班产量，查是否有空转/低产运行
   │     · 连续无产量     → 确认是否计划停机（CIP / 换型 / 检修），计划内则标记「已知」
   │     · 水/汽耗环比异常 → 查是否有跑冒滴漏、CIP 频次异常
   │
   ├─ ③ 采集链路处置（系统运维 + 电气）
   │     · 网关离线       → 见 §6.2
   │     · 单点位缺失     → 见 §6.3
   │     · 整片缺失       → 见 §6.4
   │
   └─ ④ 闭环：后台「实时告警」点「确认」，填写处置结论
          → 确认动作会写入操作审计日志
```

### 5.2 各告警类型的快速参照

| 告警文案 | 含义 | 首先做什么 |
| :--- | :--- | :--- |
| `XX 线 HH—HH 时连续 N 小时无产量` | 整点产量为 0 且电表有读数 | 核对停机计划表（CIP/换型/检修）；非计划则联系产线班长 |
| `XX 线单位电耗 X.XX，超阈值 9.60` | 当小时电耗效率差 | 查该时段是否低产运行（低产必然导致单位电耗升高，属正常物理现象） |
| `XX 线本小时预计产量 X.X 千瓶，低于额定 75%` | 当小时产能不足 | 确认是否有小停机、缺料、换型 |
| `XX 线 HH 时电表无数据，产量正常` | 有产量无电量 | 该小时单位电耗不可用；联系电气查电表通讯 |
| `车间汽耗较昨日同期 ±X%` | 蒸汽用量异常 | 查杀菌工序参数、CIP 频次、疏水阀是否泄漏 |
| `车间水耗较昨日同期 ±X%` | 用水量异常 | 查跑冒滴漏、冷却塔补水、CIP 用水 |
| `视频通道未配置转流网关` | 前端缺转流地址 | 见 §6.5 |
| `网关离线超 N 小时` | 采集网关失联 | 见 §6.2 |

## 六、故障排查手册

### 6.1 大屏打不开 / 白屏

```
① 单个终端白屏，其他终端正常
   → 该终端问题：Ctrl+F5 强制刷新 → 换浏览器 → 检查网线/网络
② 所有终端都白屏
   → 服务端问题，继续 ③
③ 检查服务
   systemctl is-active nginx
   curl -sI http://127.0.0.1/screen/ | head -3
   → 503/502：Nginx 挂了 → systemctl restart nginx
   → 403：SELinux 或权限 → 见部署文档 §3.4
   → 404：文件没部署上 → 检查 /opt/eep/screen/index.html 是否存在
④ 页面能打开但图表空白
   → 打开 F12 Console 看报错
   → Network 查 /api/energy/overview 是否返回 200 且顶层含 workshop 字段
   → 后端返回结构不符合约定是最常见原因
```

### 6.2 采集网关离线

> **先看两个时间列，再动手排查**（v1.5.2 起列表会同时给出）：
> · **最后心跳** —— 最近一次**确认它通**的时刻（采集读成功 ∪ 点位读数成功 ∪ 连接测试成功）；
> · **最近失败** —— 最近一次**确认它不通**的时刻（连接测试失败 ∪ 整轮采集全失败）。
>
> 状态按**最新证据**判定：失败时间比心跳新 → 离线。所以「有心跳却显示离线」
> 说明**其后发生过一次失败**，不是系统算错；反过来「从没成功过但一直在线」
> 在 v1.5.2 之前会出现（整轮全失败的采集也刷心跳），现在不会了。

```
① 后台确认哪台网关离线（设备与采集 → 采集网关）
   → 记下「最后心跳」与「最近失败」两个时间，判断是「从没通」还是「通了又断」
   → 点「测试连接」复测一次：
       通              → 状态立刻变「在线」（测试成功本身即为证据）
       不通（弹窗报错）→ 状态立刻变「离线」，并在列表留下「最近失败」时间
       提示无启用点位  → 网关下没有启用中的计量点，属配置问题，不是链路问题
② 网络层
   ping <网关IP>
   telnet <网关IP> <端口>          # 或 nc -zv <IP> <端口>
   → 不通：查交换机端口、网线、网关电源
③ 网关本身
   → 登录网关管理页，看是否死机（重启有效则是固件问题，需报修）
   → 查网关日志有无大量超时
④ 现场设备
   → 网关能通但读不到点位：查串口/网口接线、从站地址、波特率
   → 单表不通：查电表显示是否正常、通讯端子是否松动
⑤ 恢复后
   → 触发补采（后台 → 设备与采集 → 数据质量 → 触发补采）
   → 核对补采后的数据与现场抄表一致
```

### 6.3 单个计量点位无数据

```
① 后台 → 设备与采集 → 计量点位，找到该点位，点「测试」
② 通 → 说明协议/地址/从站都对，问题在采集程序侧 → 查后端日志
③ 不通 → 逐项核对：协议类型、IP:端口、从站地址、寄存器地址、
        数据类型（整数/浮点）、字序与字节序、变比系数
④ ⚠ 变比系数填错会直接导致该点位所有用量整体偏移（偏大或偏小一个倍数），
   校验方法：与电表本体的显示值对读一次
```

### 6.3.1 计量点位**有读数但数字明显不对** ★ 换表/接入新表先看这条

> 这类问题的共同点：**采集不报错、界面也有值**，所以很容易误判成「表坏了」或「接线错了」。
> 实际多数是**读数的解析方式**配错了。（模板：2026-10 市政水表就是这一族。）

```
① 先与**表本体显示值**对读一次，确认差值形态：
   · 整体差一个固定倍数      → 变比系数（倍率）填错
   · 数量级完全对不上/像个随机大整数 → 数据类型填错（最常见）
   · 只有小数部分不对        → 字序 / 字节序配错
② 后台 → 计量点位 → 编辑，核对这一格四项：
     数据类型  uint16/int16/uint32/int32/float32/float64
     寄存器数量（只读，由数据类型推导：16→1、32→2、64→4）
     字序      高字在前(ABCD) / 低字在前(CDAB)
     字节序    寄存器内大端(AB) / 小端(BA)
   ⚠ 现场电表与市政水表都是「大端 + 高字在前」(ABCD)，但**数据类型不同**：
     电表是 uint32，市政水表是 float64（4 个寄存器）。只改类型、不动字序/字节序。
③ 拿不准时用试读脚本把四种组合各跑一遍，**记下等于表本体值的那个组合**，
   再按 `backend/docs/采集说明.md §2.1.1` 的对照表把字序/字节序填上
   （该表给出 ABCD / CDAB / BADC / DCBA 各自对应的两项配置）。
   ⚠ 脚本里打印的「组合 3 / 组合 4」**不是**标准的 BADC / DCBA
     （它在 `byteorder='little'` 时把字节序用了两次），不要照它的标签填。
④ 改完点「试采」，确认返回读数与表本体一致；再观察 1—2 个小时的用量是否合理。
⑤ ⚠ 换表后**务必复核数据类型**：不同型号的同一用途仪表，寄存器格式可能不同。
   这一步不做，读数会「看着正常但全是错的」。
```

### 6.4 数据完整率低于 98%

```
① 后台 → 设备与采集 → 数据质量，看具体缺失时段与产线分布
② 按分布定位原因：
   · 全部产线同一时段缺失 → 网关或后端采集任务问题（单点故障）
   · 单条产线缺失         → 该线电表/计数器链路问题
   · 固定时段缺失         → 采集任务调度冲突或该时段网关负载过高
③ 处置
   · 修复链路后触发补采
   · 补不回来的时段：在报表中标注「数据缺失」，禁止插值填充
④ ⚠ 完整率低时，单位电耗等折算指标会失真，
   处置前请勿将该时段数据用于能耗考核或对外报送
```

### 6.5 视频不播放（go2rtc）

```
① 先确认一个事实：浏览器不能直接播放 rtsp://
   → 必须由 go2rtc 转成 HLS / MJPEG / MSE / WebRTC 之一
   → 链路：摄像头(RTSP) → go2rtc(:1984) → 浏览器
   → 大屏默认走 HLS → MJPEG（这两个协议前端能自己校验有没有画面）

② 检查网关
   systemctl is-active eep-stream        # 容器部署时为 docker ps | grep go2rtc
   curl -s http://<网关IP>:1984/api/streams     # 应返回 JSON，顶层 key 即可用流名
   # 浏览器直接打开 http://<网关IP>:1984/ 能看到 go2rtc 首页说明网关是活的

③ 页面提示「所有协议均无法播放」
   → 看占位里给出的「失败记录」，逐项对照
   → 最常见原因是 ② 里的流名与前端 config.ts 的 channels[*].stream 不一致（大小写敏感）

④ ★ 只有声音、没有画面（v1.1.1 已修，仍遇到时按此处置）
   → 第一件事：**量容器尺寸**（F12 选中 .video 看 getBoundingClientRect）。
     容器高度为 0 时症状与「编码不支持」一模一样 —— 有声音、没画面。
     v1.1.1 的根因就是这个（B-209），不是网关问题。
   → 再右击查看面板右上角角标的颜色/文字：
        HLS / MJPEG      前端已确证收到画面帧
        MSE / WEBRTC     由跨域 iframe 承载，前端无法校验画面有没有出（悬停角标有提示）
   → 处置：在大屏单线页按 V 键循环切换播放链路，切到 HLS → MJPEG 即可出图
        （选择写在浏览器 localStorage，刷新后保持）
   → 占位里的「失败记录」会直接写出原因，逐条对照：
        「只收到音频轨道」            浏览器不支持该视频编码，自动继续降级
        「MJPEG 拉流失败…ffmpeg…」    网关缺 ffmpeg（见 ⑥）
        「HLS 致命错误 manifestLoadError」 浏览器没连上网关 —— 检查是否
                                      页面在 localhost/公网、而网关在内网私有网段
                                      （浏览器会拦跨网段请求），或公司代理不放行内网地址
        「video 解码失败（code=3/4）」 解码失败 / 格式不支持
   → 想拿回低延迟：确认切到 MSE → MJPEG 也能出画面后，
        把 videoConfig.prefer 改成 ['mse', 'mjpeg']（只改配置，不用改代码）

⑤ 后台能看、大屏看不到
   → 先按 ④ 量容器尺寸；v1.1.1 之前确有一个「容器 0 高」的缺陷
   → 另注意大屏整屏有 transform: scale() 缩放，跨域 iframe 内的视频在缩放祖先下
     存在 Chromium 合成风险，因此大屏默认不使用 iframe 类协议（详见 docs/02 ADR-008）

⑥ 抓图 500 / MJPEG 拉不到画面
   → 网关侧缺 ffmpeg（H.264 转 JPEG 需要它）：
        curl -s "http://<网关IP>:1984/api/frame.jpeg?src=my_camera"
        返回 exec: "ffmpeg": executable file not found in %PATH%
   → HLS 与 MSE 不依赖 ffmpeg，画面本身不受影响；装 ffmpeg 并把 bin 目录加入 PATH 后重启网关
   → 详见 deploy/go2rtc/README.md「五·补、ffmpeg 依赖」

⑦ 后台「视频监控」页点「检测网关」
   → 返回「网关可达，共 N 路流」说明网关侧正常，问题在前端配置
   → 「流名不存在」说明 stream 名称写错

⑧ 画面几秒后中断
   → 只有走 Nginx 反代 /live/ 时才会遇到：必须关闭 proxy_buffering，
     并把 proxy_read_timeout 设到 3600s（长连接）
   → 浏览器直连网关（默认方式）不会有这个问题

⑨ 同时拉多路被拒
   → 海康/大华默认并发路数常见 4—6 路，每路流被一个播放端占用一份
   → go2rtc 默认按需拉流（无人观看自动断开）
   → 大屏只在打开单线详情时才播放；墙挂建议用子码流 Channels/102
   → MJPEG 兜底时网关要逐帧转 JPEG，多路同时兜底会明显吃 CPU

⑩ 大屏用 HTTPS 而网关是 HTTP
   → 浏览器会以混合内容（Mixed Content）为由拦截。内网建议统一用 HTTP

⑪ 改了 go2rtc.yaml 不生效
   → 需要重启网关：systemctl restart go2rtc
     或 Windows：powershell -File deploy\windows\nssm-install.ps1 -Action restart

完整排障手册：deploy/go2rtc/README.md
```

### 6.9 大屏与后台数字对不上（v1.4.1 新增，按此顺序查）

先别怀疑算术。这一类反馈在 v1.4.1 查到的是**四个完全不同的原因**，
用接口逐格比对一次就能分清（比对着截图猜快得多）：

```bash
# ① 逐格比对：大屏快照 vs 后台区间接口（把 D 换成被质疑的那一天）
D=2026-09-27
curl -s "http://127.0.0.1:8000/api/energy/overview?date=$D"      > /tmp/big.json
curl -s "http://127.0.0.1:8000/api/energy/range?granularity=hour&scope=all&from=$D%2000&to=$D%2023" > /tmp/adm.json
# 两边每条线 24 小时必须逐格相等；有任何一格不同，看它是不是 23 点那一格

# ② 只有 23 点差、而且大屏大一个数量级 → B-522（历史日被当成「今天」）
python -c "
import json;d=json.load(open('/tmp/big.json'))['workshop']
print('ongoingHour',d.get('ongoingHour'),'dayClosed',d.get('dayClosed'))
print('23 点：', [ (l['id'], l['hours'][23]['kwh'], l['hours'][23]['quality']) for l in d['lines'] ])"
# 查历史日时 ongoingHour 必须是 None、dayClosed 必须是 true

# ③ 日 / 月 / 年 KPI 偏小 → 汇总表落后（B-523：以前每一天都少最后一个小时）
python manage.py shell -c "
from apps.energy.models import EnergyDaily, EnergyHourly
from django.db.models import Sum
for ln in ['A1']:
  for d in ['2026-09-25','2026-09-26','2026-09-27']:
    r=EnergyDaily.objects.filter(stat_date=d,line__line_code=ln).first()
    h=EnergyHourly.objects.filter(stat_date=d,meter__line__line_code=ln,quality__in=EnergyHourly.TRUSTED).aggregate(t=Sum('consumption'))
    print(ln,d,'汇总表',r.consumption,'覆盖',r.covered_count,'| 小时表',h['t'])"
# 两者不等 或 covered_count < 24 → 补跑一次回填：
python manage.py summarize --dim day --days 10
python manage.py summarize --dim month --months 2
python manage.py summarize --dim year --years 1

# ④ 差值恒在 0.x（25 vs 24.8）→ 小数口径，v1.4.1 起两边都是 1 位小数（B-524）
#    如果又出现取整，说明有人改了 round_kwh 或前端 int() 用错了地方

# ⑤ 「数字属于另一天」：切日期时旧画面挂在新日期标签下（B-525）
#    现象：反馈的值在**前一两天**的同一格上一模一样。
#    确认日期控件徽标是否显示「正在取数 / 切换中」；没显示就是前端构建产物过期，重新发布
```

⚠ 汇总窗口必须是「昨天 + 今天」。如果发现某几天 `covered_count` 全是 23，
说明跑的是 v1.4.1 之前的旧版 `collect`（只刷今天），先确认发布版本再回填。

⚠ v1.4.2 起汇总**每天只在 00:30 结算一次**（任务 `EEP-Rollup`）。
当期（今天 / 本月 / 本年）的数字不依赖汇总表 —— 界面一律从小时表现算，
所以「今天的数在动、昨天的数却停在几天前」= `EEP-Rollup` 没跑，
先看 `backend/logs/rollup-task.log` 最后一行日期，再手工补一轮：

```bash
python manage.py summarize --rollup          # 结算昨天 + 今天 + 近 2 月 + 今年（约 1.3 秒）
```

⚠ v1.4.3 起「昨天」也有兜底：昨天的日行如果还没结算完整（缺行或 `covered_count < 24`），
接口会自动退回小时表现算。所以**任务停摆时最近两天的数字仍然正确**（只是多扫一次小时表），
停摆超过两天才会看到更早的周期停在最后一次结算那天。

⚠ 大屏挂机不用重启：v1.4.3 起跨零点会自动翻到新的一天（约 30 秒内，即下一个刷新周期）。
如果又出现「过了零点还停在昨天」，先确认发布的是新版前端 —— 那是旧版 `selectedDate`
只在页面加载时取一次日期的毛病（B-527），旧版必须手动刷新浏览器才会翻页。

### 7.2 备份策略

| 对象 | 频率 | 保留 | 方式 |
| :--- | :--- | :--- | :--- |
| 前端产物 | 每次发布前 | 5 份 | `tar -czf` 打包 |
| 后端代码 | 每次发布前 | 5 份 | Git tag + tar 快照 |
| 数据库 | 每日 02:00 | 30 天 | `pg_dump` / `mysqldump` |
| 配置文件 | 变更时 | 10 份 | 纳入 Git 管理 |
| 日志 | 按 logrotate | 30 天 | 自动轮转 |
| 采集原始数据 | 保留 7 天 | 7 天 | 数据库冷表 |

**备份命令示例（PostgreSQL）：**

```bash
# /opt/eep/ops/backup-db.sh
set -euo pipefail
TS=$(date +%Y%m%d-%H%M%S)
DIR=/backup/eep-db
mkdir -p "$DIR"

pg_dump -h 127.0.0.1 -U eep -Fc eep_db -f "$DIR/eep_db-$TS.dump"

# 校验（能读出目录结构即视为可用）
pg_restore -l "$DIR/eep_db-$TS.dump" > /dev/null

# 保留最近 30 份
ls -1t "$DIR"/eep_db-*.dump | tail -n +31 | xargs -r rm -f
echo "备份完成：$DIR/eep_db-$TS.dump"
```

### 7.3 回滚

```bash
# 前端回滚（自动取最近一次备份）
./deploy.sh rollback

# 指定版本回滚
ls -1t /opt/eep/_backup/admin-*.tar.gz | head -5
tar -xzf /opt/eep/_backup/admin-20260922-103000.tar.gz -C /opt/eep/admin

# 数据库回滚（谨慎！会丢失回滚点之后的写入）
systemctl stop eep-backend
pg_restore -h 127.0.0.1 -U eep -d eep_db --clean --if-exists /backup/eep-db/eep_db-xxx.dump
systemctl start eep-backend
```

> **回滚目标时间**：前端 ≤ 5 分钟；含数据库 ≤ 30 分钟。
> 每次发版前请把回滚命令准备好，不要等出事再查文档。

# ── 网络 ─────────────────────────────────────────────

## 十一、运维红线（禁止事项）

1. **禁止**在生产服务器上直接修改 `dist/` 里的文件。所有变更必须走构建 → 发布流程。
2. **禁止**删除 `/opt/eep/_backup` 下的全部备份。至少要保留最近 5 份。
3. **禁止**在完整率低于 98% 的时段，把折算指标（单位电耗、水/汽耗强度）用于考核或对外报送。
4. **禁止**给缺失时段插值填充。缺失就标注缺失。
5. **禁止**在未备份的情况下执行数据库恢复操作。
6. **禁止**跳过发布评审直接上线。
7. **禁止**把生产密钥、客户数据、隐私信息提交进代码库（《代码仓库管理规范》1.3 条）。
8. **禁止**关闭 SELinux / 防火墙作为长期方案（仅可临时验证，且需记录并恢复）。
9. **禁止**在没有第二人复核的情况下修改告警阈值参数。
10. **禁止**擅自变更阈值口径而不通知能源管理员。
