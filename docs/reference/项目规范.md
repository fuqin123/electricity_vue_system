# 代码仓库管理规范

## 第一章 总则

### 1.1目的

为统一总部与各地方工厂的代码托管、版本管理、协作流程和质量标准建立一个集中、安全、可审计的代码仓库
体系,特制定本规范。

### 1.2 适用范围

本规范适用于以下场景的代码托管与协作:

- **B/S架构项目:**基于浏览器的Web应用、内部管理系统、数据居看板、报表系统、API服务
- **C/S架构项目:**桌面客户端、生产线数据采集软件、本地工具软件、与硬件交互的工控程序
- **脚本:**数据处理、自动化任务、报表生成、接口对接、定时任务号、ETL脚本

### 1.3基本原则

| 原则     | 说明                                                         |
| :------- | ------------------------------------------------------------ |
| 统一托管 | 全部代码必须上传总部指定的代码仓库,严禁私自在外部平台(GitHub、个人<Gitee、SVN等)保存正式代码 |
| 可追溯   | 任何一行代码的作者,时间,原因都必须能从仓库历史中查清         |
| 可审计   | 总部对各工厂的代码库有审计权限,关键操作有日志可查            |
| 安全合规 | 严禁提交生产密钥、客户数据、隐私信息;第三方依赖必须登记在册  |
| 文档同步 | 代码与文档同步更新,禁止"代码改了文档没改“                    |
| 工厂自治 | 在规范允许范围内,各工厂对自己的代码库有自治权,总部不强制统一技术栈 |

## 第二章仓库架构

### 2.1仓库平台选型

**推荐方案:自建GitLab(部署在总部内网)**

| 维度     | 推荐做法      | 理由                      |
| -------- | ------------- | ------------------------- |
| 部署位置 | 总部内网      | 数据不出企业网,满足合规   |
| 访问方式 | VPN + SSH Key | 工厂远程访问,安全可控     |
| 认证方式 | 统一身份认证  | 一个账号通行,无需单独注册 |

**不推荐使用:**GitHub公共版、纯个人Gitee、无审计机制的免费Saas

### 2.2仓库组织形式

**采用"1+N"仓库组模式:**

```代码块
[工厂独立仓库组] 按工厂代码空间隔离
	factory-tj/ #天津工厂
    factory-cq/ #重庆工厂
    factory-xa/ #西安工厂
```

**为什么这样设计:**

- **统一规范入口:**所有项目都进同一平台,分组清晰
- **总部侧可"看到"所有代码:**BS/CS/Python项目归一管理,便于做技术资产盘点
- ·**工厂侧有独立空间:**每个工厂有自己独立的命名空间,权限可控、互不干扰
- **避免大单体仓库:**按"项目类型+工厂"二维拆分最稳

### 2.3命名规范

**仓库名/目录名**
格式: <项目类型>-<业务域>-<项目名>

| 部分     | 取值范围                                                     | 示例         |
| -------- | ------------------------------------------------------------ | ------------ |
| 项目类型 | bs / cs / py / lib                                           | bs           |
| 业务域   | plan(生产规划) / logistics (物流) / qc(品控)/eq(设备)/hr(人力)/ fin(财务)等 | plan         |
| 项目名   | 全小写、连字符分隔、≤ 30字符                                 | daily-report |

**完整示例:**

- **bs-plan-daily-report:**B/S架构+生产规划域+日报系统
- **cs-eq-collector:**C/S架构+设备域+数据采集器
- **py-logistics-dispatch:**Python脚本+物流域+调度脚本 

**禁止:**中文名、大写、特殊符号(除连字符外)、下划线命名((Python文件除外)、过长名称。

## 第三章项目分类与技术规范

### 3.1B/S架构项目

**典型代表:**日报系统、月报看板、生产排程Web端、设备状态大屏

**必备交付物**

- 前端构建产物可独立部署
- 后端API必须有OpenAPI/Swagger文档
- 必须有Dockerfile或部署文档
- 必须配置CORS、白名单、SQL注入防护
- 登录必须走统一身份认证(SSO),不允许独立账号体系

```代码块
bs-plan-daily-report/
|-- frontend/ #前端代码
    |-src/
    |-- public/
    |-- package.json
   	|-- vite.config.ts
|--backend/ #后端代码
    |-- app/
    |-- migrations/
    |-- alembic.ini
docs/
deploy/
```

前后端可以同仓,但需在README中明确目录职责。规模较大时建议拆仓

### 3.2 C/S架构项目

**典型代表:**生产线数据采集客户端、车间本地工具、设备调试伙伴
**技术栈推荐**

| 场景           | 推荐技术                            |
| -------------- | ----------------------------------- |
| Windows 客户端 | Python + PyQt5/PySide6,或C#WinForms |
| Linux工控机    | Python+PyQt,或C/C++                 |
| 跨平台         | Electron(前端),Python后端           |
| 与硬件交互     | Python + pyserial / pymodbus        |

**代码组织**

```代码块
cs-eq-collector/
	src/
        ui/ 界面层
        service/ 业务逻辑
        hardware/ #硬件交互
        sync/ #数据同步
        utils/
    resources/ #图标、配置、国际化
    build/ #打包脚本
    tests/
    docs/
		deployment.md
```

### 3.3脚本项目

**典型代表:**数据处理、自动化任务、报表生成、接口对接、定时任务

**强制要求**

| 要求       | 说明                                                 |
| ---------- | ---------------------------------------------------- |
| Python版本 | Python3.10+(统一基线)                                |
| 包管理     | pip+requirements.txt,复杂项目用 poetry               |
| 代码风格   | 遵循PEP 8+本规范第5章                                |
| 入口规范   | 必须有main.py或run.py作为入口                        |
| 配置外置   | 数据库连接、密钥等禁止硬编码,用环境变量或配置文件    |
| 日志       | 使用 logging模块,禁止 print调试                      |
| 异常处理   | 所有外部调用(API、数据库、文件)必须有try/except      |
| 重试机制   | 调用外部API必须有重试(如 tenacity库)                 |
| 幂等性     | 关键操作(写数据库、发请求)必须设计为可重复执行不出错 |

**脚本项目结构(轻量版)**

```
py-logistics-dispatch/
	--run.py
    --src/
    	-- _init__.py
        --config.py	#配置加载
        --client.py	#业务逻辑
        - utils/
	--tests/
	config.example.yaml	#配置示例(**真实配置不入库**)
    requirements.txt
    README.md
```

**定时任务脚本额外要求**

- 必须记录开始时间、结束时间、执行结果、影响行数
- 失败必须有告警(邮件/IM/电话)
- 长期任务必须有"断点续跑"能力

## 第五章代码规范

### 5.1Python编码规范

**基础:**严格遵循PEP 8。
**工具强制:**所有Python项目必须配置 pre-commit +black<+flake8+isort,提交前自动检查。

**命名约定**

| 类型   | 规则                                  | 示例                  |
| ------ | ------------------------------------- | --------------------- |
| 包名   | 全小写、连字符(目录)/下划线(Python包) | daily_report          |
| 模块名 | 全小写、可用下划线                    | report_generator.py   |
| 类名   | 大驼峰                                | class ReportGenerator |
| 函数名 | 小写+下划线                           | def generate_report() |
| 变量名 | 小写+下划线                           | user_name             |
| 常量   | 全大写+下划线                         | MAX RETRY = 3         |
| 私有   | 前缀下划线                            | internal_helper()     |

**注释与文档字符串**

- 所有公共函数、类、模块必须有docstring(Google或NumPy风格)
- 复杂逻辑必须加行注释,解释"为什么"而非"是什么"
- TODO必须写明负责人:#TODO(张三):待优化(2026-Q4处理)

```python
def calculate_achievement_rate(plan_qty: flloat, actual_qty: float) -> float:
    """计算计划达成率。
    Args:
    plan_qty:计划数量(单位:标箱)。
    actual_qty:实际完成数量(单位:标箱)。
    Returns:
    达成率(0-1之间的小数)。如果plan_qty为0,返回0.0。
    """
    if plan_qty <= 0:
    	return 0.0
    return actual_qty / plan_qty
```

### 5.2B/S项目规范

- 前端必须使用ESLint+Prettier
- 后端API必须有OpenAPI文档
- 所有接口必须鉴权(白名单接口除外,需评审通过)
- 敏感操作必须记录审计日志

### 5.3 C/S项目规范

- 必须有清晰的版本号(显示在"关于"页面)
- 本地日志至少保留30天,且按大小滚动
- 配置文件必须可手动覆盖(环境变量>配置文件>默认值)
- 必须有离线/在线模式自动切换
- 与硬件交互必须有重连机制

### 5.4第三方依赖管理

- 必须在 requirements.txt 锁定版本(含子依赖):paandas==2.2.3
- 新增依赖必须经过评审(不能用未审过的"野包")
- 每月一次依赖巡检,关注CVE安全公告
- 严禁使用GPL等强传染性许可证(除非项目本身允许)
- 国内访问慢的包建议加国内镜像源配置
