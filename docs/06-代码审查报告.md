# 能源产效管理平台 · 代码审查分析报告

> 审查方式：只读静态审查（未修改任何项目代码）。
> 审查范围：后端 Django 采集/汇总/接口层、前端大屏 `apps/screen` + 共享包 `packages/shared`、前端后台 `apps/admin` + 构建/部署配置。
> 结论基准：对照项目既有铁律（B-100~B-528、K-010 等）与实际代码逐条核验。

---

## 一、总体结论

1. **后端逻辑质量高**：差值聚合、汇总回退、`as-of` 处理、pymodbus 兼容、计划任务 `pythonw` 坑等历史铁律**均已正确落实**，未发现会让生产环境"静默产出错误数字"的后端逻辑 bug。
2. **前端框架/路由/主题合规**：路由-菜单单一数据源、Element Plus 主题集中、vite alias 与 tsconfig 一致、大屏时间正序/空值安全/单位同源等铁律**已基本正确实现**。
3. **真正的"大 bug 点"集中在三处**：①**部署白屏陷阱**（且被自检掩盖）；②**K-010 构建偶发失败**；③**数据质量面板指标失真 + 后端写入不幂等**。
4. **若干"不合理"**：前端默认直连真实接口与"框架阶段全虚拟"约定矛盾、状态文案未集中、flv 视频链路静默成功、MeterView 绕过统一占位等。

---

## 二、严重（会导致功能不可用 / 生产事故）

### 🔴 S1. 后台部署 `base` 路径不匹配 → 生产白屏（且被自检掩盖）
- **位置**：
  - `frontend/apps/admin/vite.config.ts:9` → `base: '/'`
  - `deploy/nginx/eep.conf:87-92` → `location /admin/ { alias /opt/eep/admin/; try_files $uri $uri/ /admin/index.html; }`
  - 同源问题存在于 `deploy/docker/nginx.default.conf:65-81`、`deploy/windows/web.config.admin:37`
- **现象**：所有部署形态都把后台放在子路径 `/admin/`，但 admin 的 `base` 是根 `'/'`。构建产物 `index.html` 以**根绝对路径**引用 `/assets/xxx.js`。
- **根因**：浏览器在 `/admin/` 下加载页面时，`/assets/...` 请求站点根（`/opt/eep/assets/...`），而文件实际在 `/opt/eep/admin/assets/...`，该路径不匹配 `location /admin/`，落到 server root → **404**。
- **后果**：后台整页白屏（JS/CSS 全 404）。
- **掩盖效应**：`deploy.sh`/`daily-check.sh` 用 `curl /admin/system/user` 期望 200 自检，而 history 回退返回的就是 `index.html`（200），**即使 assets 全部 404 该自检仍通过**，因此该致命问题不会被常规巡检发现。
- **建议**：部署前把 `admin/vite.config.ts` 的 `base` 改为 `'/admin/'`，并确保 Nginx `alias` 尾斜杠一致；或让部署脚本自动注入 base，而不是依赖人工"记得改"。

### 🔴 S2. K-010：`typecheck` 与 `build` 串在同一条命令 → 偶发构建失败
- **位置**：
  - `frontend/apps/admin/package.json:9` → `"build": "vue-tsc --noEmit -p tsconfig.json && vite build"`
  - `frontend/apps/screen/package.json:9` → 同结构
- **现象**：根 `build`（串行 `pnpm build:screen && pnpm build:admin`，B-201 已合规）最终仍把 `vue-tsc` 与 `vite build` 拼在同一条 shell 命令里执行。
- **后果**：这正是铁律 K-010 点名的"pnpm build 偶发失败"根因——vue-tsc 与 vite 任一异常都导致整轮构建流产。
- **建议**：各 app 的 `build` 改为仅 `vite build`（或复用已存在的 `build:only`），typecheck 走独立命令（根 `typecheck` 已是 `pnpm -r --workspace-concurrency=1`，合规）。

## 三、中等（数据失真 / 健壮性 / 一致性）

### 🟠 M1. `dataConfig.mode` 默认 `'api'`，与"框架阶段全虚拟"铁律冲突
- **位置**：`frontend/packages/shared/src/config.ts:115` → `mode: 'api' as 'mock' | 'api'`
- **现象**：记忆铁律第三条写明"数据全部为虚拟数据（`config.ts → dataConfig.mode = 'mock'`）"，但代码实际默认 `'api'` + `mockOnly` 屏蔽未实现域。代码注释自称"现场默认"。
- **后果**：已实现域（energy.*、admin meters/lines/gateways/quality/collect-logs/params/readings）会打真实后端；而后端就绪状态不明时，这些页直接报错/空白，且把"演示数据保护层"失效。记忆与代码矛盾，属于**配置口径不一致**。
- **建议**：明确当前所处阶段。若确为现场接入，则更新记忆铁律；若仍是框架/演示期，应改回 `'mock'` 或让 `request()` 在未达后端时自动回退 mock。

### 🟠 M2. `QualityBars` 把"电量上报率"当成"产量上报率"展示（指标失真）
- **位置**：`frontend/apps/screen/src/components/QualityBars.vue:15`（单一 `rate`）、`:32-39`（电量/产量两行共用 `rate`）；调用方 `LineView.vue:193-201`（`stat` 仅按 `kwh` 统计）、`:398`
- **现象**：`rate` 由 `received/expect` 算出，而 `received/expect` 只数 `s.kwh !== null`。于是"产量上报"一行显示的是电量上报率。
- **后果**：产量未接入时产量全为 null，产量上报率应为 0%，却显示电量率（常近 100%）→ 误导；即便产量接入后，电量缺失≠产量缺失，两率仍会互相串。
- **建议**：分别统计 `kwh` 与 `output` 的 received/expect，或明确该面板只反映电量、改名"电量上报质量"。

### 🟠 M3. 大屏 `LineView` 中列缺 `panel--grow` → 三列底边不齐（违反 B-517）
- **位置**：`frontend/apps/screen/src/views/LineView.vue:383`（board）、`:404`/`:406`/`:432`（中列三块均为固定高）
- **现象**：中列 = KpiCards(118 固定) + 趋势 PanelBox(486 固定) + 热力图 PanelBox(276 固定)，**三块无一传 `grow`**；而左列（本线小时明细为 grow）、右列（本线告警为 grow）都撑满 board 高 → 中列热力图底边明显高于左右两列。同类页面 `OverviewView` 中列末块正确地不传 height（`:306`）→ 三列对齐。
- **后果**：单线详情主屏（大屏二）三列底边不齐，可见布局缺陷。
- **建议**：给中列末块热力图 PanelBox 去掉固定 `height`（或中列任一面板加 grow）。

### 🟠 M4. 状态文案未集中 + 同 `LineStatus` 跨组件标签不一致（违反"状态文案集中"铁律）
- **位置**：
  - `frontend/apps/screen/src/components/LineList.vue:13-17`（`slow → '低产'`）
  - `frontend/apps/screen/src/views/LineView.vue:113-129`（`slow → '低负荷（按用电）'`）
  - `VideoMonitor.vue:40-46`（`STATE_TEXT`）、`LineView` 内 `statusChip` 各自硬编码
- **现象**：`LineStatus='slow'` 在 LineList 标"低产"、在 LineView 标"低负荷（按用电）"，同义不同词；线状态、视频状态映射未集中到 `shared/src/format.ts`（目前仅 `HOUR_QUALITY_LABEL` 集中了小时质量文案）。
- **后果**：产量接入切换时文案口径漂移，现场易误读；同状态多份拷贝后期必脱节。
- **建议**：在 `shared/src/format.ts` 增 `LINE_STATUS_LABEL` / `VIDEO_STATE_LABEL`，各组件统一引用。

### 🟠 M5. `VideoMonitor` flv 分支提前 `done(true)` → 静默成功、无降级（违反视频链路铁律）
- **位置**：`frontend/apps/screen/src/components/VideoMonitor.vue:380-397`（`done(true)` 在 `player.load()` 后立即调用）
- **现象**：flv 分支在 `attachMediaElement/load/play` 之后**立即** `done(true)`，随后 `player.on(ERROR, () => done(false))` 因 `settled` 已为 true 被忽略。
- **后果**：若 flv 实际播放失败，组件不会降级到 hls/webrtc，只静默停在黑屏，违背"失败必须 `fail()` 记录原因不许静默"的链路铁律（仅影响 `provider='custom'` 路径，现场默认 `go2rtc` 不受影响）。
- **建议**：待首帧/`MANIFEST_PARSED` 后再 `done(true)`，错误先 `done(false)` 触发降级（参考 hls 分支）。

### 🟠 M6. `MeterView` 写操作绕过统一的 `notImplemented()` 占位约定
- **位置**：`frontend/apps/admin/src/views/device/MeterView.vue`（全文无 `notImplemented`；`saveMeter :176`、`doTest :227`、`doDelete :255` 直调 `adminApi`）
- **现象**：全工程其他写按钮均走 `notImplemented()`，唯独此页"新增/编辑/试采/删除"走 `adminApi.saveMeter/testMeter/deleteMeter`（因 `admin.meters` 在 `mockOnly`，实际走 mock 并弹 `ElMessage`）。
- **后果**：UX 不一致，易让人以为该功能已上线；后端就绪后这个"框架页"会真的往库里写。
- **建议**：要么统一改为 `notImplemented()`（符合铁律），要么在代码注释中明确"MeterView 是有意做成可写 mock"并说明理由。

### 🟠 M7. 后端：明文生产凭证驻留 `settings.local.yaml` + token 走 HTTP 查询串
- **位置**：
  - `backend/config/settings.local.yaml:20`（MySQL root 口令 `310460`）、`:112`（平台 token `9sP7kG23`）
  - `backend/apps/energy/collectors/http_api.py:95`（token 拼进查询串）
- **现象**：口令与 token 明文写入 `settings.local.yaml`（已核实**未入库**，example 用 `CHANGE_ME` 占位，无泄漏）；HTTP 采集器把 token 拼进查询串，经 HTTP 明文传输易被中间人截获。
- **后果**：工程目录一旦被打包/同步/备份，真实口令与 token 直接外泄；明文 token 传输存在被截获风险。
- **建议**：口令/token 一律走环境变量（`EEP_DB_PASSWORD` 等，settings.py 已支持覆盖）；平台接口改 HTTPS，token 放进请求头而非 URL。

### 🟠 M8. 后端：`bulk_create` 不幂等 → 重叠/并发采集轮次整轮回滚丢数
- **位置**：`backend/apps/energy/services/collect.py:95`（`EnergyRaw.objects.bulk_create(readings, batch_size=200)`）
- **现象**：同一小时内两次采集同时落库，`uk_raw_meter_time`（唯一键 `(meter, collect_time)`）触发 `IntegrityError`，整轮 `transaction.atomic`（`collect.py:94`）回滚、本轮读数全丢。`collect_loop.py:73` 不带 `--if-due` 可直接采，与计划任务 `collect --aggregate --if-due` 可并行；且每次 `collect` 末尾无条件跑 `aggregate_recent(hours=2)`。
- **后果**：慢轮次触发下一轮时，后一轮在 `bulk_create` 处抛错、被 `run_task` 捕获返回 1，该轮读数丢失（重试可部分弥补，但存在缺口窗口与日志噪声）。
- **建议**：`bulk_create(..., ignore_conflicts=True)`；或入库前按 `(meter_id, collect_time)` 去重；并让 `collect_loop` 与计划任务互斥（文件锁/单实例）。

## 四、轻微（视觉/健壮性/代码异味）

- **B-520 el-table 普遍用固定 `width` 右侧留白**：`GatewayView/HistoryView/RuleView/RealtimeView/QualityView/MeterView/OperationLogView/ReportView/ProductView/LineListView/LoginLogView/CollectLogView/DictView/ParamView/RoleView/UserView` 列定义处系统性误用 `width:`；仅 `ElectricView/UtilityUsageView/ReadingQueryView` 遵守 `minWidth`。建议数据列改 `minWidth`（操作列 `fixed="right"` 固定宽度合理）。
- **ChartPanel `setOption` 无 try/catch（B-521 潜伏）**：`frontend/apps/admin/src/components/ChartPanel.vue:26-30`，一旦某序列 `yAxisIndex` 越界会按 B-521 中断整棵子树挂载、症状表现为"同页 el-table 列消失"。当前各 option 自洽无实时故障，建议加 try/catch + console.error。
- **`.npmrc` 冗余工作区级键**：`frontend/.npmrc:7,10`（`node-linker`/`store-dir`）与 `pnpm-workspace.yaml` 重复；v10 起以 yaml 为准，功能无碍但误导维护者，建议删除。
- **docker-compose 版本漂移 + 缺后端镜像构建**：`deploy/docker/docker-compose.yml:24,45` 镜像打 `1.1.0`，而 `frontend/package.json:3` 已是 `1.4.4`；`Dockerfile` 仅构建 frontend，未提供 backend 构建上下文，`--profile backend up` 引用不存在的后端镜像会失败。
- **ReadingQueryView 的 `extraQuery` 冗余**：`ReadingQueryView.vue:224` 每次渲染新建对象且 `fetchReadings` 实际不消费它（直接读 ref），建议去掉或真正并入筛选条件。
- **死代码/坏味道**：`useEcharts.ts:109-113` 的 `useViewport` 全仓无调用点；`LineList.vue:46` 用 `void pad2;` 抑制未用导入。
- **后端小裂缝（不致错误数字，但易在维护时被改坏）**：`summary.py:476-479` 车间级覆盖率有死代码且取 `min` 语义可疑；`summary.py:178-187` `EnergyDaily/Monthly` 的 `stat_year/stat_month` 永不被写入（当前读路径无影响，潜伏不一致）；`api.py:1177/1197/1218` 写操作 `int()` 强转非数值 → 偶发 500（建议校验返回 400）；迁移 `0006` 用 f-string 拼表名（来源为常量，非注入风险，仅代码异味）。
- **OverviewView KPI 用 `h?.partial` 推"进行中"（B-518 轻微偏差）**：`OverviewView.vue:123`，应改 `h?.hour === w.currentHour` 以消除语义耦合（其他点已正确用 `ongoingHour/currentHour`）。

## 五、已正确实现的铁律（值得肯定，审查中已逐条核实）

- **后端**：B-501（pymodbus `slave`/`device_id` 按签名探测）、B-502（RTU 帧 + `retries=1`）、B-503/504（端点取最近 + 进行中小时≥2条）、B-505（聚合 `sum(空)=None`）、B-509（序列化层无裸 `float()`，全仓 `float()` 带 `is not None` 守卫）、B-510（状态取最近已结束小时）、B-522（`as-of` 改 `closed=True`）、B-523（滚动窗口含昨天，统一 `refresh_rollups`）、B-528（`_day_not_settled` 仅今天/昨天回退）、`collect_task.py` 用 `pythonw` 安全 `run_task`。
- **前端大屏/共享包**：B-512（趋势时间正序、无 `reverse()`）、B-513（空值安全 `scale()`、`connectNulls:false`）、B-514（单位与除数同源 `OVERVIEW_TREND`/`LINE_TREND`）、B-515（缺数留空不画假曲线）、B-518（进行中仅由 `hour===currentHour` 推出，仅 m3 轻微偏差）、B-526（`types.ts` 已声明 `kwh: number | null`）、B-527（`today` 用 `ref` + 定时器 `syncToday()`，非 `computed(()=>new Date())`）。
- **前端后台/构建**：B-201（根 `build` 串行）、B-519（`useEnergyUsage` 把 `ready` 并入 `extraQuery`）、B-521（energyUsageOption 已修正 yAxis 序列）、路由/菜单单一数据源一致、图标缺失安全降级、主题集中 `element-override.scss`、vite alias 与 tsconfig paths 三处一致、密钥已脱敏。

## 六、优先级建议（Top 3 最危险）

1. **S1 部署白屏陷阱（含自检掩盖）**——最隐蔽也最致命：后台在所有部署形态下大概率白屏，且常规巡检 `curl /admin/...` 返回 200 会掩盖它。需在部署链路或构建脚本中固化 `base` 与 `alias` 的一致性。
2. **S2 K-010 构建稳定性**——typecheck 与 vite build 不应串同一条命令，否则偶发失败且拖累整轮发布。
3. **M2 质量面板指标失真 / M8 后端写入不幂等丢数**——前者是"看得见但数字错"的误导，后者是"生产环境静默丢数"的潜伏风险，二者都直接动摇系统可信度。
