## 二、现场取数方式

### 2.1 电表：485 串口服务器（Modbus RTU over TCP）

现场 4 台串口服务器，每台后面挂一条 RS485 总线，总线上并着多块电表：

| 网关编号 | 位置 | 地址 | 挂的表（从站号） |
| :--- | :--- | :--- | :--- |
| `GW-PDB-1` | 一期配电房串口服务器 1 口 | `10.112.66.41:8891` | 三线生产线1(13)、三线生产线2(15)、三线吹瓶机(6)、五线生产线(8)、五线吹瓶机(7) |
| `GW-PDB-3` | 一期配电房串口服务器 3 口 | `10.112.66.41:8893` | 二线生产线(7)、二线吹瓶机(5) |
| `GW-PDB-4` | 一期配电房串口服务器 4 口 | `10.112.66.41:8894` | 一线生产线(8)、一线吹瓶机(6) |
| `GW-TASHI` | 一期配电房塔石 | `10.112.66.133:8890` | 四线生产线(11)、五线冰水机(14)、六线生产线(10)、六线吹瓶机(7) |

**读法（已实测核对）**

```
功能码   03（读保持寄存器）
起始地址 1000
寄存器数 2（32 位无符号，高字在前）
倍率     0.1  →  kWh
请求帧   08 03 03 E8 00 02 <CRC16>            ← 从站号 + 功能码 + 地址 + 数量 + CRC
响应帧   08 03 04 03 C3 3B 79 41 99
                 └─4 字节数据─┘ └CRC┘
          0x03C33B79 = 63,126,393  →  6,312,639.3 kWh
```

> ⚠ **必须用 RTU 组帧，不能用 Modbus TCP 组帧。**
> 串口服务器只是「把 RS485 报文塞进 TCP」，没有 Modbus TCP 的
> `事务号 + 协议号 + 长度 + 单元号` 头。用错帧器会一直超时，看起来像现场断线。
> 参考实现：`E:\http_test\serial_servier.py`（现场已验证）。

## 三、数据怎么存、怎么算

### 3.1 三张核心表

```
eep_gateway  采集网关（串口服务器 / HTTP API）
eep_meter    计量点（13 块电表 + 蒸汽总表 + 水总表占位）
eep_reading  ★ 原始读数：每次采样存一条**累计值**（如 6,312,645.0 kWh）
eep_hourly_usage  ★ 小时用量：每小时一条，**交付给大屏的就是它**
eep_collect_log   每轮采集的日志（成功/失败点位、耗时、错误原因）
eep_line          产线主数据（A1—A6）
```

**为什么原始读数也要留**：出问题能复查、换表能看出断点、算法改了能直接重算差值，
不用等现场重新采集。保留 180 天（`manage.py purge_readings` 清理），
**小时用量永久保留**。

### 3.2 小时差值口径

对小时 H（如 14:00—15:00）：

```
usage(H) = end(H) − end(H−1)
end(H)   = 「时间 ≤ H+1:00:00」的最后一条有效读数（距整点最近的那次采样）
```

用「上小时末读数」当起点，而不是「本小时第一条读数」，好处是：
相邻两小时首尾相接，不漏计也不重复计；采集中断后恢复，也不会把中断期间的用量
错算进某一个小时（端点离整点太远会被判成 `partial`）。

`eep_hourly_usage.quality` 的取值与含义：

| quality | 触发条件 | 用量值 | 是否进产线/车间合计 |
| :--- | :--- | :--- | :--- |
| `ok` | 正常 | 有值 | ✅ 只有它能进 |
| `partial` | 端点离整点超过 20 分钟（中途采集中断过） | 有值但仅供参考 | ❌ |
| `missing` | 缺读数 | **null** | ❌ |
| `reset` | 累计值回退（换表 / 表归零） | **null** | ❌ |
| `spike` | 差值 > 该表 `max_hourly`（断讯补传、换表瞬间） | 保留数值 | ❌ |

### 3.2.1 采集节奏（v1.2.2 起：每小时一次）

配置在 `config/settings.yaml`：

```yaml
collect:
  cadence: hourly              # hourly（现场默认）| minute
  hourly_offset_seconds: 60    # 整点后多少秒采样
  interval_seconds: 60         # 仅 minute 节奏使用
```

**hourly 节奏下每个小时的值实际覆盖 `[H:00+60s, (H+1):00+60s]`**，即整体后移 60 秒。
这是离散采样的固有性质（不可能在整点那一瞬间取到值）；
关键是**两个端点偏移相同**，所以区间严格等于 1 小时，不会累积偏差。

| | hourly（默认） | minute |
| :--- | :--- | :--- |
| 差值区间 | 严格 1 小时 | 约 1 小时，随轮次耗时漂移（一轮 1.4 秒，跑一小时能偏出十几秒） |
| 与现场节奏 | 与抄表 / 结算一致 | — |
| 数据量 | 1 | 60 |
| 当前小时参考值 | **算不出来**，界面显示「待整点采集」 | 随时可给 |
| 单点失败影响 | 一次失败影响相邻两个小时 | 有冗余，影响小 |

> **切换节奏只改配置，不用改代码** —— 两种节奏的差值口径完全一致。

#### 运行方式（推荐：计划任务 + 幂等守卫）

```bash
# 每 5 分钟跑一次；--if-due 先检查本小时采样是否已完成，完成就跳过
python manage.py collect --aggregate --if-due
```

`--if-due` 的判定标准是「**每一个启用中的计量点**在本小时都已经有读数」。
用「全部」而不是「任意」，是为了容忍采集中途被打断 ——
那时只有部分点位有读数，下一次运行会把整轮重跑一遍
（多出来的读数无害：差值取的是距整点最近的那一条）。

于是「每 5 分钟跑一次」等价于「每小时采一次」，而万一某次因机器重启 /
网络抖动没跑成，**下一个 5 分钟会自动补上** —— 比「每小时准点跑一次、错过就丢一小时」可靠得多。

也可以直接跑常驻循环（自己按节奏睡眠）：

```bash
python manage.py collect_loop
```

### 3.2.2 端点怎么取（B-502 / B-503 换来的）

```
usage(小时 H) = read(H+1:00) − read(H:00)
read(边界 B)  = 距 B 最近的一条有效读数，且必须落在 B ± 20 分钟内
```

三条规则，每条都对应一个真实缺陷：

1. **取「最近」而不是「该边界之前的最后一条」。**
   同一采样槽可能因失败重试出现多条读数（`--if-due` 就是每 5 分钟重试）。
   取最近时槽内第一条永远胜出；若取「之后最后一条」，一次 10:30 的补采
   会把 09:01→10:30 这 89 分钟当成「09 点这一小时」，09 点多算、10 点少算，
   两条又都会因为偏离 1 小时被判 partial 而不计入合计 —— 现场只看到「这几小时没数据」。
2. **必须有容差下限。**
   老实现只写了 `at <= 边界` 这一个上界。本小时根本没采到样时，
   它会一路往前找到几小时前、甚至隔天的读数来相减 ——
   两条陈旧读数相减通常正好得 **0**，且不触发任何异常分支、只被标成 partial。
   界面上一看就是「这一小时一点电都没用」：量级正常、没有报错、没有告警。
   现在超出容差直接判**缺数**，界面显示 `--`。
3. **容差同时覆盖两种节奏**：密采样时最近的是整点前最后一条（差几十秒），
   整点采样时最近的是槽内第一条（差几分钟）。

现场核对用：

```bash
python manage.py aggregate --verify --date 2026-09-23 --hours 9,10
```

它会逐条打印**起点读数、终点读数、两条读数各自的时刻、相隔多少分钟、差值、判定质量** ——
只看库里一个数没法判断对错，看端点才能。

### 3.3 三条不能破的口径（都对应真实踩坑）

1. **缺数绝不补 0。** 补 0 在图上就是「产量暴跌」，会被当成产线停了。
   缺就是 `null`，前端画成虚线/留空。
2. **任何负数差值都丢掉。** 换表、表归零会产生负值或巨大尖峰，一旦进入合计，
   当天的电量就废了。判 `reset` 并记原因。
3. **合计宁可空白，不给偏小值。** 某小时只要有一块表缺数/换表，该小时**产线合计就是 null**，
   而不是「有几块算几块」。偏小的数比空白更危险 —— 它看起来是正常的。

> 这三条与前端 `mock/energy.ts` 的 B-100—B-108 是同一套口径，前后端不要各写一套。

### 3.4 当前小时怎么显示

正在进行的小时用「最新读数 − 参考起点」给一个参考值，标 `partial` 并带 `progress`
（这个值实际覆盖了小时的多长时间）：

- 正常情况下起点 = 上小时末读数，`progress` = 本小时已过时间占比；
- 刚部署 / 采集中断后的第一个小时没有「上小时末读数」，就用**本小时第一条读数**当基线，
  此时 `progress` 只覆盖很短一段 —— 界面上不会把它误当成整小时的平均水平。

Windows 计划任务 —— 每 5 分钟唤起一次，`--if-due` 决定这一轮采不采：

```powershell
# 入口脚本负责把输出写进 backend/logs/collect-task.log，再交给 Django
$pyw    = "C:\eep\venv\Scripts\pythonw.exe"        # 必须用 venv 里的，见下方说明
$script = "C:\eep\backend\scripts\collect_task.py"
schtasks /Create /TN "EEP-Collect" /SC MINUTE /MO 5 /F /TR ('"{0}" "{1}"' -f $pyw, $script)
```

> **为什么必须经过 `scripts/collect_task.py`，不能直接 `pythonw manage.py collect`：**
> `pythonw.exe` 没有控制台，此时 `sys.stdout` 是 `None`；而 Django 的 `BaseCommand`
> 会把它包进 `OutputWrapper`，之后每条 `self.stdout.write(...)` 都要走到
> `None.write(...)` → `AttributeError`。结果是**不留痕迹地失败**：不弹窗、不输出、
> 一次都没采到，计划任务里只看到一个非零退出码 —— 现场看到的现象却是
> 「任务在跑，但设备一直没数据」。
> 入口脚本先把 stdout / stderr 接到日志文件，再交给 Django；顺带把工作目录切到
> `backend/`（计划任务的默认工作目录是 `C:\Windows\System32`）。
>
> ⚠ 用 `pythonw.exe` 时请用**装了依赖的那个解释器**（venv 里的），
> 不要用系统 Python 的 —— 那个环境里没有 Django / PyMySQL / pymodbus。

Linux crontab（等价写法，`--if-due` 同样生效）：

```cron
*/5 * * * * cd /opt/eep/backend && /opt/eep/venv/bin/python manage.py collect --aggregate --if-due >> /var/log/eep/collect.log 2>&1
```

常用运维命令：

```powershell
schtasks /Query  /TN "EEP-Collect" /FO LIST /V     # 上次结果 / 下次运行时间
schtasks /Run    /TN "EEP-Collect"                 # 手工触发一轮
schtasks /Change /TN "EEP-Collect" /DISABLE        # 暂停（排障用，别忘恢复）
schtasks /Delete /TN "EEP-Collect" /F
```

任务日志：`backend/logs/collect-task.log`（超过 2 MB 自动轮转一份 `.log.1`）。
每轮一行，「跳过」和「真采了」都看得出来：

```text
──── 2026-09-23 10:41:39 采集任务开始（collect --aggregate --if-due）────
本小时的采样已完成，跳过（节奏：每小时一次（整点后 60 秒采样，随后做差得出上一小时用量））。
2026-09-23 10:41:40 结束：正常，耗时 0.8s
```

### 4.2.1 `--if-due` 何时采、何时跳过（现场最常问的一个）

**两个条件同时满足才采：**

| 条件 | 含义 | 不满足时 |
| :--- | :--- | :--- |
| ① 本小时的采样时刻已到 | 整点 + `collect.hourly_offset_seconds`（默认 60 秒） | 直接退出。这条不能省 —— 否则计划任务若在整点触发就会在 `H:00:00` 瞬间读表，把刻意留出的避让窗口（避开整点采集竞争与表内累计刷新）绕过去 |
| ② 每个启用中的计量点在本小时都有 `ok` 读数 | 现场标准 = 14/14 全部拿到 | **再跑一轮** —— 这就是重试机制 |

所以「每 5 分钟跑一次」的实际行为是：

```text
10:01  采全 14 点
10:05  跳过   10:10 跳过   10:15 跳过   …… 10:55 跳过      ← 本小时已完成
11:00  跳过                                                  ← 还没到采样时刻
11:05  到点了 → 采集
         └─ 假设 11:05 有几路失败 → 11:10 再跑整轮 → 11:15 再跑 …… 直到本小时采全
```

两点必须知道：

1. **重试是「整轮重跑」**，会对全部启用点位重新读一遍。多出来的读数无害 ——
   `boundary_reading` 取的是「距整点最近的一条」，采样槽内第一条永远胜出。
2. **重试的有效窗口只到本小时结束。** 过了整点，这个采样槽就过去了；之后补采到的
   读数离整点太远，会被判 `partial` / 缺数（见 `aggregate.py` 的端点容差与相位判定），
   **不计入合计**。也就是说：**失败拖满一小时 = 永久丢掉这一个小时的数据**，无法事后补。
   想多留几次「干净」的重试机会，把触发间隔由 5 分钟改成 1 分钟（`/MO 1`）即可 ——
   `pythonw` 不弹窗，代价只是任务日志多几行。

`collect_loop`（常驻循环）也可用，适合手工跑或临时部署。

### 4.3 定时任务的时间预算

单点最坏耗时 = `timeout_ms × (1 + retry_times)`。当前配置 `1500ms × 2 = 3s`，
**13 块电表全部掉线也只要 39 秒** —— 无论是 5 分钟的触发间隔，还是 1 小时的采样槽，
都远够用，不会出现任务堆积。改超时 / 重试参数时请重新算一遍这个预算，
并确认「单点最坏耗时 × 点位数 < 触发间隔」。

`unitKwh` 为 null、`plan` / `rate` 为 0；也不拿电量去反推产量 ——
大屏上宁可空着，也不能出现看起来像真的假数字。真实产量经 `ingest_production` 写入后自动恢复数值口径。

> 电量拿不到时返回 `null`（不是 0）。前端若切到 `dataConfig.mode = 'api'`，
> 需要把 `types.ts` 里水/汽的 `today` / `yesterday` 从 `number` 放宽为 `number | null`。

## 七、踩坑记录（改代码前先看）

### 7.1 `pymodbus` 的 `retries=0` 会静默失败 ★

```python
ModbusTcpClient(host, port=port, framer=FramerType.RTU, retries=0)   # ❌ 全部读不到
ModbusTcpClient(host, port=port, framer=FramerType.RTU, retries=1)   # ✅ 正常
```

传 `retries=0` 时 pymodbus 3.7 **根本不把请求发出去**，13 块表全部返回
`No Response received from the remote slave`，看起来像现场 485 断线或从站号写错，
实际是自己没发。实测：正常点 66—127ms；从站不存在时正好耗时一个 timeout（不会翻倍）。

### 7.2 串口服务器的帧类型

`framer=FramerType.RTU` 不能省，也不能换成默认的 TCP 帧器（见 §2.1）。

### 7.3 「合计宁可空白，不给偏小值」

一开始的实现是「有几块表算几块」，结果一块表掉线时合计偏小但看起来正常，
比空着更容易误导。现在只要有一块表缺数，该小时合计就是 `null`。

### 7.4 `progress` 不能用「本小时已过时间占比」

刚部署时的参考值基线是本小时第一条读数，只覆盖很短窗口。
用「已过时间占比」会让人以为这是整小时的平均水平
（实测踩过：41 分钟显示 0.8 kWh，容易被读成产线停了）。
