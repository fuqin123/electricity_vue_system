## 二、现场取数方式

### 2.1 电表：485 串口服务器（Modbus RTU over TCP）

现场 4 台串口服务器，每台后面挂一条 RS485 总线，总线上并着多块电表：

| 网关编号 | 位置 | 地址 | 挂的表（从站号） |
| :--- | :--- | :--- | :--- |
| `GW-PDB-1` | 一期配电房串口服务器 1 口 | `10.112.66.41:8891` | 三线生产线1(13)、三线生产线2(15)、三线吹瓶机(6)、五线生产线(8)、五线吹瓶机(7) |
| `GW-PDB-3` | 一期配电房串口服务器 3 口 | `10.112.66.41:8893` | 二线生产线(7)、二线吹瓶机(5) |
| `GW-PDB-4` | 一期配电房串口服务器 4 口 | `10.112.66.41:8894` | 一线生产线(8)、一线吹瓶机(6) |
| `GW-TASHI` | 一期配电房塔石 | `10.112.66.133:8890` | 四线生产线(11)、五线冰水机(14)、六线生产线(10)、六线吹瓶机(7) |

**读法（已实测核对）**

```
功能码   03（读保持寄存器）
起始地址 1000
寄存器数 2（32 位无符号，高字在前）
倍率     0.1  →  kWh
请求帧   08 03 03 E8 00 02 <CRC16>            ← 从站号 + 功能码 + 地址 + 数量 + CRC
响应帧   08 03 04 03 C3 3B 79 41 99
                 └─4 字节数据─┘ └CRC┘
          0x03C33B79 = 63,126,393  →  6,312,639.3 kWh
```

> ⚠ **必须用 RTU 组帧，不能用 Modbus TCP 组帧。**
> 串口服务器只是「把 RS485 报文塞进 TCP」，没有 Modbus TCP 的
> `事务号 + 协议号 + 长度 + 单元号` 头。用错帧器会一直超时，看起来像现场断线。
> 参考实现：`E:\http_test\serial_servier.py`（现场已验证）。

#### 2.1.1 数据类型不是「一律 32 位整数」（v1.5.3）★ 换表必读

上面的「2 个寄存器、32 位无符号」**只是电表的读法**。现场并非所有表都如此：

> **碳水市政水表 `W-CARB-CITY-1`（`GW-WATER-CTY` `10.114.1.71:10123`、从站 5、起始地址 68）
> 是 4 个寄存器、IEEE754 双精度（double）。**

按 32 位整数去拼这块表，会得到一个**完全无关的大整数** ——
采集不报错、小时差值照算，只有数字荒谬。现场核对时的表现是「水表读数不对」，
而不是「配置错了」，很容易往水表本体或接线方向查。

因此每个计量点都要配**数据类型**（后台「计量点」表单里的「数据类型」下拉）：

| 数据类型 | 寄存器个数 | 说明 |
| :--- | :--- | :--- |
| `uint16` / `int16` | 1 | 16 位整数 |
| `uint32` / `int32` | 2 | 32 位整数 —— **现场 13 块电表的读法**（默认值） |
| `float32` | 2 | 32 位浮点 IEEE754 |
| `float64` | 4 | 64 位双精度 / double —— **市政水表** |

**寄存器个数是推导值**：由数据类型决定（16 位→1、32 位→2、64 位→4），
后台表单里显示为只读，不要手填。填错读取长度不会报错，只会给出一个荒谬的读数。

**字序 / 字节序**决定「4 个寄存器怎么拼回一个数」，两层含义不同：

| | 含义 | 取值 |
| :--- | :--- | :--- |
| **字序** `word_order` | **寄存器之间**的顺序 | `big` 高字在前（ABCD，现场常用）/ `little` 低字在前（CDAB） |
| **字节序** `byte_order` | **单个寄存器内部**两个字节的顺序 | `big` 高字节在前（AB，现场常用）/ `little` 低字节在前（BA） |

两者组合即工业上通用的四种排布：

| 排布 | 字节序 | 字序 | 64 位寄存器序列 |
| :--- | :--- | :--- | :--- |
| **ABCD** | big | big | R0 R1 R2 R3 —— **现场电表与市政水表都是这一种** |
| CDAB | big | little | R3 R2 R1 R0 |
| BADC | little | big | 每个寄存器内部字节对调，字序不变 |
| DCBA | little | little | 每个寄存器内部字节对调，且字序颠倒 |

> ⚠ 现场试读脚本（`parse_double`）里的**「组合 3 / 组合 4」不要拿来对照**：
> 它在 `byteorder='little'` 时既对调寄存器内字节、又整体按小端解释，
> 等于把字节序用了两次，打印出来的并不是标准 BADC/DCBA。
> 该脚本里真正有意义的是**组合 1（ABCD）**，而系统实现与它在组合 1、2 上逐位一致。

**换表 / 接入新表时的核对顺序**（`W-CARB-CITY-1` 就是这样确认的）：

1. 用试读脚本把四种组合都跑一遍，**记下哪一个等于表本体显示的值**；
2. 在后台把该点位的「数据类型 / 字序 / 字节序」配成对应组合；
3. 点「试采」，确认返回的读数与表本体一致；
4. 如果三种组合都对不上，别急着改代码 —— 先确认**起始地址**（跟仪表走，
   现场绝大多数是 1000，市政水表是 68）与**从站号**。

> ⚠ 本机（开发机）连不到 `10.114.1.71`，水表只能在目标机上验证；
> 其余 13 块电表的数据类型本次未动，解码结果逐位不变。

## 三、数据怎么存、怎么算

### 3.1 三张核心表

```
eep_gateway  采集网关（串口服务器 / HTTP API）
eep_meter    计量点（13 块电表 + 蒸汽总表 + 水总表占位）
eep_reading  ★ 原始读数：每次采样存一条**累计值**（如 6,312,645.0 kWh）
eep_hourly_usage  ★ 小时用量：每小时一条，**交付给大屏的就是它**
eep_collect_log   每轮采集的日志（成功/失败点位、耗时、错误原因）
eep_line          产线主数据（W103 / W101 / W102 / W301 / W104 / W105）
```

**为什么原始读数也要留**：出问题能复查、换表能看出断点、算法改了能直接重算差值，
不用等现场重新采集。保留 180 天（`manage.py purge_readings` 清理），
**小时用量永久保留**。

### 3.2 小时差值口径

对小时 H（如 14:00—15:00）：

```
usage(H) = end(H) − end(H−1)
end(H)   = 「时间 ≤ H+1:00:00」的最后一条有效读数（距整点最近的那次采样）
```

用「上小时末读数」当起点，而不是「本小时第一条读数」，好处是：
相邻两小时首尾相接，不漏计也不重复计；采集中断后恢复，也不会把中断期间的用量
错算进某一个小时（端点离整点太远会被判成 `partial`）。

`eep_hourly_usage.quality` 的取值与含义：

| quality | 触发条件 | 用量值 | 是否进产线/车间合计 |
| :--- | :--- | :--- | :--- |
| `ok` | 正常 | 有值 | ✅ 只有它能进 |
| `partial` | 端点离整点超过 20 分钟（中途采集中断过） | 有值但仅供参考 | ❌ |
| `missing` | 缺读数 | **null** | ❌ |
| `reset` | 累计值回退（换表 / 表归零） | **null** | ❌ |
| `spike` | 差值 > 该表 `max_hourly`（断讯补传、换表瞬间） | 保留数值 | ❌ |

### 3.2.1 采集节奏（v1.2.2 起：每小时一次）

配置在 `config/settings.yaml`：

```yaml
collect:
  cadence: hourly              # hourly（现场默认）| minute
  hourly_offset_seconds: 60    # 整点后多少秒采样
  interval_seconds: 60         # 仅 minute 节奏使用
```

**hourly 节奏下每个小时的值实际覆盖 `[H:00+60s, (H+1):00+60s]`**，即整体后移 60 秒。
这是离散采样的固有性质（不可能在整点那一瞬间取到值）；
关键是**两个端点偏移相同**，所以区间严格等于 1 小时，不会累积偏差。

| | hourly（默认） | minute |
| :--- | :--- | :--- |
| 差值区间 | 严格 1 小时 | 约 1 小时，随轮次耗时漂移（一轮 1.4 秒，跑一小时能偏出十几秒） |
| 与现场节奏 | 与抄表 / 结算一致 | — |
| 数据量 | 1 | 60 |
| 当前小时参考值 | **算不出来**，界面显示「待整点采集」 | 随时可给 |
| 单点失败影响 | 一次失败影响相邻两个小时 | 有冗余，影响小 |

> **切换节奏只改配置，不用改代码** —— 两种节奏的差值口径完全一致。

#### 运行方式（推荐：计划任务 + 幂等守卫）

```bash
# 每 5 分钟跑一次；--if-due 先检查本小时采样是否已完成，完成就跳过
python manage.py collect --aggregate --if-due
```

`--if-due` 的判定标准是「**每一个启用中的计量点**在本小时都已经有读数」。
用「全部」而不是「任意」，是为了容忍采集中途被打断 ——
那时只有部分点位有读数，下一次运行会把整轮重跑一遍
（多出来的读数无害：差值取的是距整点最近的那一条）。

于是「每 5 分钟跑一次」等价于「每小时采一次」，而万一某次因机器重启 /
网络抖动没跑成，**下一个 5 分钟会自动补上** —— 比「每小时准点跑一次、错过就丢一小时」可靠得多。

也可以直接跑常驻循环（自己按节奏睡眠）：

```bash
python manage.py collect_loop
```

### 3.2.2 端点怎么取（B-502 / B-503 换来的）

```
usage(小时 H) = read(H+1:00) − read(H:00)
read(边界 B)  = 距 B 最近的一条有效读数，且必须落在 B ± 20 分钟内
```

三条规则，每条都对应一个真实缺陷：

1. **取「最近」而不是「该边界之前的最后一条」。**
   同一采样槽可能因失败重试出现多条读数（`--if-due` 就是每 5 分钟重试）。
   取最近时槽内第一条永远胜出；若取「之后最后一条」，一次 10:30 的补采
   会把 09:01→10:30 这 89 分钟当成「09 点这一小时」，09 点多算、10 点少算，
   两条又都会因为偏离 1 小时被判 partial 而不计入合计 —— 现场只看到「这几小时没数据」。
2. **必须有容差下限。**
   老实现只写了 `at <= 边界` 这一个上界。本小时根本没采到样时，
   它会一路往前找到几小时前、甚至隔天的读数来相减 ——
   两条陈旧读数相减通常正好得 **0**，且不触发任何异常分支、只被标成 partial。
   界面上一看就是「这一小时一点电都没用」：量级正常、没有报错、没有告警。
   现在超出容差直接判**缺数**，界面显示 `--`。
3. **容差同时覆盖两种节奏**：密采样时最近的是整点前最后一条（差几十秒），
   整点采样时最近的是槽内第一条（差几分钟）。

现场核对用：

```bash
python manage.py aggregate --verify --date 2026-09-23 --hours 9,10
```

它会逐条打印**起点读数、终点读数、两条读数各自的时刻、相隔多少分钟、差值、判定质量** ——
只看库里一个数没法判断对错，看端点才能。

### 3.3 三条不能破的口径（都对应真实踩坑）

1. **缺数绝不补 0。** 补 0 在图上就是「产量暴跌」，会被当成产线停了。
   缺就是 `null`，前端画成虚线/留空。
2. **任何负数差值都丢掉。** 换表、表归零会产生负值或巨大尖峰，一旦进入合计，
   当天的电量就废了。判 `reset` 并记原因。
3. **合计宁可空白，不给偏小值。** 某小时只要有一块表缺数/换表，该小时**产线合计就是 null**，
   而不是「有几块算几块」。偏小的数比空白更危险 —— 它看起来是正常的。

> 这三条与前端 `mock/energy.ts` 的 B-100—B-108 是同一套口径，前后端不要各写一套。

### 3.4 当前小时怎么显示

正在进行的小时用「最新读数 − 参考起点」给一个参考值，标 `partial` 并带 `progress`
（这个值实际覆盖了小时的多长时间）：

- 正常情况下起点 = 上小时末读数，`progress` = 本小时已过时间占比；
- 刚部署 / 采集中断后的第一个小时没有「上小时末读数」，就用**本小时第一条读数**当基线，
  此时 `progress` 只覆盖很短一段 —— 界面上不会把它误当成整小时的平均水平。

## 四、部署与运行

### 4.1 依赖与建库

```bash
cd backend
pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple

# 建库（只需一次；字符集必须 utf8mb4）
mysql -uroot -p -e "CREATE DATABASE IF NOT EXISTS eep_energy \
  DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;"

cp config/settings.example.yaml config/settings.local.yaml   # 填数据库口令与平台 token
python manage.py migrate          # 建表
python manage.py seed_registry    # 把设备登记表同步进库
```

配置优先级：**环境变量 > `config/settings.local.yaml` > `config/settings.example.yaml`**。
生产环境的口令请用环境变量注入（`EEP_DB_PASSWORD`），不要写进文件。

### 4.2 日常运行

```bash
python manage.py collect                 # 采一轮（14 个点位，约 1.4 秒）
python manage.py collect --dry-run       # 只读不写库（现场接线排障用）
python manage.py aggregate --recent 2    # 重算最近 2 个已结束的小时
python manage.py aggregate --date 2026-09-22 --show   # 重算整天并打印明细
python manage.py purge_readings --days 180            # 清理过期原始读数
python manage.py runserver 0.0.0.0:8000  # 接口服务
```

**生产环境用系统计划任务，别依赖常驻进程**（崩溃不会自愈）。

Windows 计划任务 —— 每 5 分钟唤起一次，`--if-due` 决定这一轮采不采：

```powershell
# 入口脚本负责把输出写进 backend/logs/collect-task.log，再交给 Django
$pyw    = "C:\eep\venv\Scripts\pythonw.exe"        # 必须用 venv 里的，见下方说明
$script = "C:\eep\backend\scripts\collect_task.py"
schtasks /Create /TN "EEP-Collect" /SC MINUTE /MO 5 /F /TR ('"{0}" "{1}"' -f $pyw, $script)
```

★ **还有一个必须存在的每日任务**（v1.4.2 起）—— 日 / 月 / 年汇总的结算：

```powershell
$script = "C:\eep\backend\scripts\daily-rollup-task.py"
schtasks /Create /TN "EEP-Rollup" /SC DAILY /ST 06:30 /F /TR ('"{0}" "{1}"' -f $pyw, $script)
```

| 任务 | 频率 | 干什么 |
| :--- | :--- | :--- |
| `EEP-Collect` | 每 5 分钟 | 采读数 + 算小时差值（`collect --aggregate --if-due`），**不碰汇总表** |
| `EEP-Rollup` | 每天 06:30 | 结算生产日 / 月 / 年（`summarize --rollup` = 上一生产日 + 当前生产日 + 近 2 月 + 近 2 年） |

为什么定在 06:30：生产日到次日 06:00 才结束，05—06 点的差值要等 06:xx 采到跨日边界读数
才算得出来（B-523 / v1.6.0），06:30 既有裕量又赶在白班交接前。

> 测试 / 生产共用设备时，可在测试环境的 `settings.local.yaml` 设
> `collect.hourly_offset_seconds: 600`，让测试在整点后第 10 分钟采样；
> collector 每轮对齐 5 分钟刻度，失败也在下一刻度重试。仓库默认值仍按生产配置。

⚠ **停掉 `EEP-Rollup` 不会报错，但大屏与后台的「近 30 日 / 近 12 月」会停在最后一次
结算的那一天**（当期数字是现算的所以还在动，最容易让人误判成「系统只坏在旧数据上」）。
巡检时看一眼 `backend/logs/rollup-task.log` 最后一行的日期即可。

> **为什么必须经过 `scripts/collect_task.py`，不能直接 `pythonw manage.py collect`：**
> `pythonw.exe` 没有控制台，此时 `sys.stdout` 是 `None`；而 Django 的 `BaseCommand`
> 会把它包进 `OutputWrapper`，之后每条 `self.stdout.write(...)` 都要走到
> `None.write(...)` → `AttributeError`。结果是**不留痕迹地失败**：不弹窗、不输出、
> 一次都没采到，计划任务里只看到一个非零退出码 —— 现场看到的现象却是
> 「任务在跑，但设备一直没数据」。
> 入口脚本先把 stdout / stderr 接到日志文件，再交给 Django；顺带把工作目录切到
> `backend/`（计划任务的默认工作目录是 `C:\Windows\System32`）。
>
> ⚠ `pythonw.exe` 必须来自**装了本项目依赖的那个解释器**。
> 本机当前用的是 `D:\python3.13.10\pythonw.exe` —— 实测该环境为
> Django 6.0.7 + pymodbus 3.15.0（比 `requirements.txt` 锁的 5.1.4 / 3.7.4 新），
> 干跑与实采均 **14/14 点位正常**，写库、差值、汇总也都正常。
> 指向一个没装依赖的解释器时，日志里只有一行表头加一段 `ModuleNotFoundError` 回溯 ——
> 看着像「任务在跑」，实际一条数据都没采到。
> **生产环境建议按 `requirements.txt` 单独建 venv，再把任务指向它**（版本可复现）。

### 4.2.1 `--if-due` 何时采、何时跳过（现场最常问的一个）

**两个条件同时满足才采：**

| 条件 | 含义 | 不满足时 |
| :--- | :--- | :--- |
| ① 本小时的采样时刻已到 | 整点 + `collect.hourly_offset_seconds`（默认 60 秒） | 直接退出。这条不能省 —— 否则计划任务若在整点触发就会在 `H:00:00` 瞬间读表，把刻意留出的避让窗口（避开整点采集竞争与表内累计刷新）绕过去 |
| ② 每个启用中的计量点在本小时都有 `ok` 读数 | 现场标准 = 14/14 全部拿到 | **再跑一轮** —— 这就是重试机制 |

所以「每 5 分钟跑一次」的实际行为是：

```text
10:01  采全 14 点
10:05  跳过   10:10 跳过   10:15 跳过   …… 10:55 跳过      ← 本小时已完成
11:00  跳过                                                  ← 还没到采样时刻
11:05  到点了 → 采集
         └─ 假设 11:05 有几路失败 → 11:10 再跑整轮 → 11:15 再跑 …… 直到本小时采全
```

两点必须知道：

1. **重试是「整轮重跑」**，会对全部启用点位重新读一遍。多出来的读数无害 ——
   `boundary_reading` 取的是「距整点最近的一条」，采样槽内第一条永远胜出。
2. **重试的有效窗口只到本小时结束。** 过了整点，这个采样槽就过去了；之后补采到的
   读数离整点太远，会被判 `partial` / 缺数（见 `aggregate.py` 的端点容差与相位判定），
   **不计入合计**。也就是说：**失败拖满一小时 = 永久丢掉这一个小时的数据**，无法事后补。
   想多留几次「干净」的重试机会，把触发间隔由 5 分钟改成 1 分钟（`/MO 1`）即可 ——
   `pythonw` 不弹窗，代价只是任务日志多几行。

`collect_loop`（常驻循环）也可用，适合手工跑或临时部署。

### 4.3 定时任务的时间预算

单点最坏耗时 = `timeout_ms × (1 + retry_times)`。当前配置 `1500ms × 2 = 3s`，
**13 块电表全部掉线也只要 39 秒** —— 无论是 5 分钟的触发间隔，还是 1 小时的采样槽，
都远够用，不会出现任务堆积。改超时 / 重试参数时请重新算一遍这个预算，
并确认「单点最坏耗时 × 点位数 < 触发间隔」。

## 七、踩坑记录（改代码前先看）

### 7.1 `pymodbus` 的 `retries=0` 会静默失败 ★

```python
ModbusTcpClient(host, port=port, framer=FramerType.RTU, retries=0)   # ❌ 全部读不到
ModbusTcpClient(host, port=port, framer=FramerType.RTU, retries=1)   # ✅ 正常
```

传 `retries=0` 时 pymodbus 3.7 **根本不把请求发出去**，13 块表全部返回
`No Response received from the remote slave`，看起来像现场 485 断线或从站号写错，
实际是自己没发。实测：正常点 66—127ms；从站不存在时正好耗时一个 timeout（不会翻倍）。

### 7.2 串口服务器的帧类型

`framer=FramerType.RTU` 不能省，也不能换成默认的 TCP 帧器（见 §2.1）。

### 7.3 「合计宁可空白，不给偏小值」

一开始的实现是「有几块表算几块」，结果一块表掉线时合计偏小但看起来正常，
比空着更容易误导。现在只要有一块表缺数，该小时合计就是 `null`。

### 7.4 `progress` 不能用「本小时已过时间占比」

刚部署时的参考值基线是本小时第一条读数，只覆盖很短窗口。
用「已过时间占比」会让人以为这是整小时的平均水平
（实测踩过：41 分钟显示 0.8 kWh，容易被读成产线停了）。

## 七·五、告警评估挂在哪儿（v1.5.4）

告警不是常驻服务，而是**由任务顺带评估**，所以排任务时要知道落点：

| 触发点 | 评估范围 | 说明 |
| :--- | :--- | :--- |
| `collect`（每 5 分钟计划任务 / collector 容器） | 全部规则 | 放在「有失败就返回非 0」之前 —— 部分失败的那一轮恰恰最该生成告警。覆盖率规则此时只读**日终后已重算**的上一生产日行，06:30 结算前的当天快照不参与判定（B-553 / v1.6.0） |
| `summarize --rollup`（每天 06:30 / rollup 容器） | 全部规则 | 覆盖率规则读的是刚写下的上一生产日日汇总行，结算完立刻评估 |
| `review_abnormal`（review 容器，每分钟） | 仅 `hour_deviation` | 到达 `data_quality.review_hour` 后扫描上一生产日 partial 小时，生成差值/时段告警；每天只执行一次 |
| 大屏读路径 `/api/energy/overview` | **只有 `collect_stale`** | 采集进程一旦死掉就没人评估告警，而「采集停了」恰是最该被看见的一条，所以由读路径兜底（不累加 `repeat`） |
| `python manage.py check_alerts` | 全部规则 | 只查不采（不想去碰设备时用这个）；`--json` 给巡检脚本 |

手工补算或验证：

```bash
python manage.py check_alerts            # 评估并列出未处理告警
python manage.py check_alerts --json     # 给巡检脚本
```

⚠ 新增规则时要同时改三处：`services/alerts.py` 的 `_RULES`、
`docs/api-contract.md` §4.4 的规则表、后台「告警规则」页 `RuleView.vue` 的清单。
只改代码的话，那一页就会继续谎报系统在监控什么。

**覆盖率规则的时间语义（v1.6.0）：** `energy_daily` 里同一天的两种行必须分清 ——
已结束生产日的行是结论，当前生产日 06:30 写下的行只是「到此刻」的快照。`_rule_coverage`
只有在该行 `computed_at` 晚于**次日 06:25 的结算门槛**时才判定缺数
（门槛不取 06:00：rollup 在 06:00–06:30 重启会立刻补跑，最后一小时的边界读数可能还没到）；同时会把仍处于
`active` / `acked` 的覆盖率告警所属日期一并复核，因此真实缺数不会因为日期翻篇
被 `resolve_stale` 误恢复。改动这条规则时，务必保留「恢复必须有重新评估的证据」。

## 七·六、生产日与读数差值（v1.6.0）

### 7.6.1 一个「日」是 06:00—次日 06:00

- 生产日 D = `[D 06:00, D+1 06:00)`，标签用开始日期。
- `energy_daily.stat_date` 仍存日期，但语义改成生产日开始日；`expected_count` 仍是 24。
- 日汇总取 `energy_hourly` 的 `(D, 06..23)` + `(D+1, 00..05)`；开始日 00—05 和
  次日 06—23 不属于本生产日。
- 月 / 年仍由日行累加，所以「日加起来 = 月 = 年」；月 / 年窗口也是从当月/当年
  1 日 06:00 到次月/次年 1 日 06:00。
- 结算：`EEP-Rollup` 每天 06:30；覆盖率门槛 06:25。

口径切换后必须重建一次：

```bash
python manage.py rebuild_summaries --dry-run   # 看范围
python manage.py rebuild_summaries             # 清空三张汇总表后按生产日重算
```

### 7.6.2 仪表读数查询的「小时差值」

`/api/admin/readings` 给每条原始读数补一个 `hourUsage`：它是**以该读数为终点**
结算出的上一小时差值，直接读 `energy_hourly`（`end_at == collect_time`），
不在接口里用相邻原始读数现减 —— 否则补采、跨槽、峰值剔除的口径会与小时表分叉。

- 没有匹配行：`hourStatus = pending`（最新读数，下一小时尚未结算）或
  `not_boundary`（不在整点 ±20 分钟窗口，不参与差值）；
- 有行但 `consumption = NULL`：显示 `--`，质量按 `missing/reset` 标注；
- `spike/partial`：数值照给，但标注「不计入合计 / 仅供参考」，绝不补 0。

## 七·七 异常时段与人工复核（v1.7.1）

- 后台「系统参数 → 数据质量」：
  - `data_quality.deviation_minutes`（默认 10）：端点相位 / 区间时长在此范围内视为正常；
  - `data_quality.review_hour`（默认 11，可含小数，11.5=11:30）：每天复核触发时刻。
- 超出允许范围但仍有差值的 partial 小时**不再丢弃**：计入日/月/年汇总和图表，
  汇总 quality 仍标 partial；missing/reset/spike 仍不计。
- 到达复核时刻后，上一生产日的 partial 小时生成 `hour_deviation` 告警：
  `value` 是差值、`threshold` 是实际时段；需人工确认，不自动恢复。
- 未执行复核时 partial 数据照常写入/显示；`energy_review_log` 保证每天只复核一次。
