## 一、与草案的 8 处差异（每处都是现场情况决定的）

| # | 你的草案 | 本项目设计 | 为什么 |
| :--- | :--- | :--- | :--- |
| 1 | 未包含设备表 | **新增 `energy_meter`（计量点/仪表）** | 采集必需。一块表 = 一个 RS485 从站，要记网关、从站号、寄存器地址、功能码、字序、倍率，或 HTTP 取值路径。没有它就无法采集，也无法按你的要求在后台维护仪表 |
| 2 | `energy_raw` 唯一键 `(line_id, energy_type_id, collect_time)` | 唯一键 `(meter_id, collect_time)`；另建 `(line_id, energy_type_id, collect_time)` **普通索引** | **采集主体是表，不是产线** —— 一条产线有 2—3 块表（三线 3 块、五线 3 块），按产线唯一就必须在采集时先求和，**丢掉单表读数**，现场再也答不出「三线吹瓶机那一路是不是坏了」。你要的「按产线 + 能源类型 + 时间查」由普通索引覆盖 |
| 3 | `line_id INT NOT NULL` | **保持 NOT NULL**；车间水/汽总表挂一条「车间哨兵行」（`line_code=WORKSHOP`，`line_type=workshop`） | 水、汽只有车间总表，不属于任何产线。若把 `line_id` 设为可空来容纳它，MySQL 的唯一索引会把多个 `NULL` 视为**互不相同** —— 汇总表的唯一键`(line_id, energy_type_id, 周期)` 对总表就**形同失效**，重复行能照样插进去。用一条真实记录承载，唯一键处处有效；界面按 `line_type` 过滤，看不到它 |
| 4 | 未包含小时表 | **新增 `energy_hourly`（小时用量）** | 日/月/年**只能由小时差值累加得出，不能由「日末读数 − 日初读数」**：采集若断了 5 小时，后者照样给出一个数，把缺的那段静默吞掉、看起来一切正常（这正是本项目反复在修的「假数字」类问题，见 `docs/02` 的 B-502）。小时表还携带质量标记 `ok/partial/missing/reset/spike`，是数字可信度的唯一凭据 |
| 5 | `consumption DECIMAL(18,4) NOT NULL` | **可空** | 本项目铁律「**缺数绝不补 0**」：0 在能耗语境里是「确实没用」，与「没采到」语义正好相反。写成 NOT NULL + default 0，等于把「没采到」硬说成「用了 0」 |
| 6 | 汇总表只有 `consumption` | 增加 `quality` + `covered_*` / `expected_*` | 没有覆盖度，界面无法区分「今日用了 300 kWh」和「今日只统计到 2 个小时、共 300 kWh」——后者会被读成「今天几乎没用电」（B-403 现场踩过） |
| 7 | `production_line` 只放 6 条产线 | 增加 1 条**车间哨兵行**（`line_type='workshop'`，`line_code='WORKSHOP'`） | 让汇总表的 `line_id` 能保持 NOT NULL、唯一键有效（车间级水汽总表要落进日/月/年）。后台「生产管理 → 产线」按 `line_type` 过滤，列表里看不到它 |
| 8 | 未含产量相关表 | 保留 `production_hourly`（未来产量接入用） | **产量不是一种能源**，不该混进 `energy_*` 汇总表。单位电耗（kWh/千瓶）在查询时用 `energy_daily(ELECTRIC)` ÷ 产量算出来，两边各自可空 |

**没有采纳的草案内容（附理由）**

| 草案建议 | 处理 | 理由 |
| :--- | :--- | :--- |
| `energy_raw` 按 `collect_time` 按月分区 | **本期不做**，DDL 备查（见 §六） | 数据量：14 点位 × 24 小时 = **336 行/天 ≈ 12 万行/年**，MySQL 单表毫无压力。而分区会带来「每个唯一键都必须包含分区键」等限制，现阶段收益为负 |
| 用一张通用汇总表 `energy_summary`（`period_type` + `period_value`） | **采纳分开三张表** | 与你的判断一致：日/月/年拆开，字段与索引更直白，「上月对比上月」这类查询不用额外过滤 `period_type` |

## 二、表清单与关系

```text
production_line ──┬──< energy_meter ──< energy_raw ──(差值)──> energy_hourly
                  │         │
                  │         └── energy_gateway          （一块表属于一个网关）
                  ├──< production_hourly                （产量，未接入）
                  └──< energy_daily / energy_monthly / energy_yearly
energy_type ──────┴──（被 energy_meter / energy_raw / energy_hourly / 三级汇总引用）
```

| 表 | 中文名 | 粒度 | 说明 |
| :--- | :--- | :--- | :--- |
| `production_line` | 产线（含车间行） | 一行一条产线 | 6 条产线 + 1 条车间哨兵 |
| `energy_type` | 能源类型 | 一行一种能源 | `ELECTRIC` / `WATER` / `STEAM` |
| `energy_gateway` | 采集网关 | 一行一个网关 | 4 台串口服务器 + 1 个平台 API |
| `energy_meter` | 计量点（仪表） | 一行一块表 | 设备参数 + 归属产线与能源类型 |
| `energy_raw` | 原始读数 | **小时 × 计量点** | 累计值（如 6,312,639.3 kWh） |
| `energy_hourly` | 小时用量 | **小时 × 计量点** | 差值 + 质量标记（交付给逐时图表的就是它） |
| `energy_daily` | 日汇总 | 日 × 产线 × 能源类型 | 由 `energy_hourly` 累加 |
| `energy_monthly` | 月汇总 | 月 × 产线 × 能源类型 | 由 `energy_daily` 累加 |
| `energy_yearly` | 年汇总 | 年 × 产线 × 能源类型 | 由 `energy_daily` 累加 |
| `production_hourly` | 小时产量 | 小时 × 产线 | **产量未接入**，仅 null 占位 |
| `energy_collect_log` | 采集日志 | 一行一轮 | 后台「采集日志」页读它 |

## 三、表结构明细

标注：**【草案原样】** = 按你给的设计实现；**【调整】** = 有改动，理由见 §一；**【新增】** = 草案里没有。

### 3.1 `production_line` 产线表

| 字段 | 类型 | 说明 | 来源 |
| :--- | :--- | :--- | :--- |
| `id` | INT PK AUTO_INCREMENT | 产线 ID | 【草案原样】 |
| `line_code` | VARCHAR(50) UNIQUE | 产线编码，如 `A1` | 【草案原样】 |
| `line_name` | VARCHAR(100) | 产线名称，如 `一线` | 【草案原样】 |
| `status` | TINYINT | 1 启用 / 0 停用 | 【草案原样】 |
| `created_at` | DATETIME | 创建时间 | 【草案原样】 |
| `line_type` | VARCHAR(10) | `line` / `workshop` | 【新增】区分产线与车间哨兵行（§一.7） |
| `rated` | INT | 额定产能（瓶/小时） | 【调整】静态台账参数，没有它算不出计划产量与达成率 |
| `product` | VARCHAR(64) | 品项（如 冰红茶 500ml） | 【调整】同上，大屏要显示 |
| `sort` | INT | 排序 | 【调整】大屏产线列表顺序 |
| `updated_at` | DATETIME | 更新时间 | 【新增】 |

### 3.2 `energy_type` 能源类型表

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | INT PK AUTO_INCREMENT | 能源类型 ID |
| `type_code` | VARCHAR(20) UNIQUE | `WATER` / `ELECTRIC` / `STEAM` |
| `type_name` | VARCHAR(50) | 水 / 电 / 汽 |
| `unit` | VARCHAR(20) | `m³` / `kWh` / `t` |
| `sort` | INT | 排序（大屏水电气顺序） |
| `enabled` | TINYINT | 预留 |

全部【草案原样】。

> ⚠ 水的单位按你的草案写 `m³`。现场水表尚未接入（接口地址待提供），
> 接入时请确认流量计输出的到底是体积（m³）还是质量（t）—— 两者不可换算，写错会让水耗指标整体偏。

### 3.3 `energy_raw` 原始数据表

| 字段 | 类型 | 说明 | 来源 |
| :--- | :--- | :--- | :--- |
| `id` | BIGINT PK AUTO_INCREMENT | 自增主键 | 【草案原样】 |
| `meter_id` | INT NOT NULL | 计量点 ID | 【调整】采集主体（§一.2），唯一键用它 |
| `line_id` | INT NOT NULL | 产线 ID（车间级总表挂哨兵行） | 【调整】保持非空，用哨兵行承载车间级（§一.3） |
| `energy_type_id` | INT NOT NULL | 能源类型 ID | 【草案原样】 |
| `collect_time` | DATETIME NOT NULL | 采集时间（精确到小时） | 【草案原样】 |
| `reading` | DECIMAL(18,4) | 累计读数 | 【调整】**可空**：采集失败要留痕 |
| `ok` | TINYINT | 本次采集是否成功 | 【新增】失败读数不能参与差值（否则会把 0 当真实读数） |
| `raw` / `error` | VARCHAR(200) | 原始报文 / 错误信息 | 【新增】现场排障的唯一线索 |
| `created_at` | DATETIME DEFAULT CURRENT_TIMESTAMP | 入库时间 | 【草案原样】 |

索引：

```sql
UNIQUE KEY uk_raw_meter_time (meter_id, collect_time)      -- 防重复采集（§一.2）
INDEX idx_raw_line_time (line_id, energy_type_id, collect_time)  -- 你草案里要的按产线+类型查
INDEX idx_raw_collect_time (collect_time)                  -- 按时间范围归档
```

### 3.4 `energy_hourly` 小时用量表【新增】

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | BIGINT PK AUTO_INCREMENT | 自增主键 |
| `meter_id` | INT NOT NULL | 计量点 |
| `line_id` | INT NOT NULL | 产线（车间级挂哨兵行） |
| `energy_type_id` | INT NOT NULL | 能源类型 |
| `stat_date` | DATE NOT NULL | 归属日期 |
| `stat_hour` | TINYINT NOT NULL | 归属小时 0—23 |
| `consumption` | DECIMAL(18,4) NULL | 本小时用量（缺数 = NULL，**不补 0**） |
| `unit` | VARCHAR(20) | 单位（冗余，导出时不用连表） |
| `quality` | VARCHAR(10) | `ok` / `partial` / `missing` / `reset` / `spike` |
| `start_reading` / `end_reading` | DECIMAL(18,4) NULL | 差值用的两个端点累计值 |
| `start_at` / `end_at` | DATETIME NULL | 两个端点各自的采样时刻 |
| `note` | VARCHAR(200) | 判定说明（现场看这一列就知道为什么是 partial） |
| `computed_at` | DATETIME | 计算时间 |

```sql
UNIQUE KEY uk_hourly (meter_id, stat_date, stat_hour)
INDEX idx_hourly_period (stat_date, stat_hour)
```

> **`quality` 的取值决定它算不算进日/月/年**：只有 `ok` 进合计。
> `partial`（端点偏离整点）、`missing`（缺数）、`reset`（累计值回退，换表）、
> `spike`（超上限）一律不进合计，但**值仍然留着**，便于现场复核。

### 3.5 `energy_daily` 日汇总表

| 字段 | 类型 | 说明 | 来源 |
| :--- | :--- | :--- | :--- |
| `id` | BIGINT PK | 自增主键 | 【草案原样】 |
| `line_id` | INT NOT NULL | 产线 ID | 【草案原样】 |
| `energy_type_id` | INT NOT NULL | 能源类型 ID | 【草案原样】 |
| `stat_date` | DATE NOT NULL | 统计日期 | 【草案原样】 |
| `consumption` | DECIMAL(18,4) **NULL** | 当日消耗量 | 【调整】可空（§一.5） |
| `start_reading` / `end_reading` | DECIMAL(18,4) NULL | 日初 / 日末读数 | 【草案原样】 |
| `covered_hours` / `expected_hours` | SMALLINT | 已覆盖 / 应有小时数 | 【新增】覆盖度（§一.6） |
| `quality` | VARCHAR(10) | `ok` / `partial` / `missing` | 【新增】 |
| `unit` | VARCHAR(20) | 单位 | 【新增】 |
| `created_at` / `updated_at` | DATETIME | 创建 / 更新时间 | 【草案原样】 |

```sql
UNIQUE KEY uk_daily (line_id, energy_type_id, stat_date)
```

### 3.6 `energy_monthly` 月汇总表

同 `energy_daily`，`stat_month DATE`（存当月第一天）+ `covered_days` / `expected_days`：

```sql
UNIQUE KEY uk_monthly (line_id, energy_type_id, stat_month)
```

### 3.7 `energy_yearly` 年汇总表

同 `energy_daily`，`stat_year SMALLINT`（如 2026）+ `covered_days` / `expected_days`：

```sql
UNIQUE KEY uk_yearly (line_id, energy_type_id, stat_year)
```

> 月/年**由日行累加**而不是直接扫小时表：一是速度，二是三者口径天然一致
> （月 = 该月各日之和），不会出现「日加起来不等于月」。

## 四、数据流（谁产生谁）

```text
采集（每小时整点 + 60s 偏移）
  └─> energy_raw        累计读数（meter × 时刻），唯一键防重
        └─ 差值（usage = end − start，±20 分钟容差 + 相位判定）
             └─> energy_hourly   小时用量 + quality
                   └─ 只累加 quality='ok'
                        ├─> energy_daily    日 × 产线 × 能源类型
                        │     └─> energy_monthly ─> energy_yearly
                        └─> 接口 /api/energy/*  →  大屏 / 后台
```

**接口层不直接读 `energy_raw`**：那是累计值，前端要的是「用了多少」。
累计值的唯一用途是「复核」——`manage.py aggregate --verify` 会把它打印出来。

## 六、分区 DDL（本期不启用，供数据量上来后使用）

`energy_raw` 数据量到千万级（约 80 年以上）之前不需要分区。确需启用时：

```sql
-- 月分区（分区键 collect_time，必须包含在每个唯一键里 —— 我们的唯一键已满足）
ALTER TABLE energy_raw
  PARTITION BY RANGE COLUMNS (collect_time) (
    PARTITION p202609 VALUES LESS THAN ('2026-10-01'),
    PARTITION p202610 VALUES LESS THAN ('2026-11-01'),
    PARTITION pmax    VALUES LESS THAN (MAXVALUE)
  );
```

历史归档 = `ALTER TABLE ... DROP PARTITION p202609`，秒级完成，不锁全表。

## 七、对外接口不受影响（前端零改动）

接口路径、响应结构与 v1.2.x **完全一致**，只换了底层表。两个需要留意的映射：

| 接口字段 | 新库来源 | 说明 |
| :--- | :--- | :--- |
| `meters[].kind` | `energy_meter.energy_type.type_code` → 映射 `ELECTRIC→elec`、`WATER→water`、`STEAM→steam` | 前端 `MeterPoint.kind` 用的是短码，故在接口层做一次映射；`category`（电/水/汽）取 `type_name` |
| `period-summary.items[].kwh` / `waterT` / `steamT` | `energy_daily` 按 `energy_type` 三列取出后横向拼装 | 外部契约仍是一行含三种能源（与 `EnergySnapshot` 一致），内部才是按能源类型分行 |
| `unitKwh` | `energy_daily(ELECTRIC).consumption ÷ 产量` | 产量未接入时为 `null`，不用 0 兜底 |

## 八、迁移实录（在真实库上跑出来的三个坑）

按 §五 的步骤在现有库（15 个计量点、1246 条读数、跨 09-22~09-24）上真跑了一遍迁移，
撞出三个问题。它们**都不是假想的**，而是「库里的历史数据与设计不匹配」造成的，
写在这里供以后再迁移时直接对照：

| # | 现象 | 根因 | 处理 |
| :--- | :--- | :--- | :--- |
| 1 | `Duplicate entry 'line-day-2026-09-22' for key 'uniq_period_summary'` | 旧汇总表要删掉 `line` 列，而 MySQL 删列会**重建唯一索引**；旧唯一键是 `(scope, line, dim, period_key)`，6 条产线的行只在 `line` 上不同，删掉后剩下的三元组立刻互相重复 | 该表在迁移末尾会被整个删除，所以在**迁移第一步**先 `DELETE` 清空它 |
| 2 | `Duplicate entry '14-2026-09-22 17:18:00' for key 'uk_raw_meter_time'` | **旧 `eep_reading` 根本没有唯一约束**，库里本来就存在同一秒的重复读数（实测：meter_id=14 在 2026-09-22 17:18:00 有两条）—— 这正是新设计要加的约束在起作用 | 加约束前按 `(meter_id, collect_time)` 去重，保留 `id` 最大的一条（实测删掉 1 条） |
| 3 | `Unknown column 'line_type'` / `x.line_id` | **操作顺序**：回填 SQL 用到了后面才 `AddField` 的列 | 回填之前必须先加列：产线三列（`created_at`/`line_type`/`updated_at`）与 `raw`/`hourly` 的 `line` 全部前移到回填之前 |

另外两条顺序约束（同样是实测）：
- **旧索引 / 旧唯一约束的删除必须放在字段改名之前**（在 0005 里）。它们引用的旧字段名
  （`date` / `kind` / `at`）一旦被 `RenameField` 改掉，MySQL 删索引时要按字段名定位 → `KeyError`。
- **新增的必填外键一律「先可空 → 回填 → 改非空」**（0006 加可空列 + 回填，0007 收紧为 NOT NULL）。
  直接是非空会写不进已有行，而给一个默认值又等于凭空造数据。
